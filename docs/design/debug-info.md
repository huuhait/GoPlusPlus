# Debug information (P04.12, D4.7)

One class, `DebugInfoBuilder` (`compiler/include/gopp/CodeGen/DebugInfo.h`, `lib/CodeGen/DebugInfo.cpp`), makes all the debug metadata. `LowerToLLVM.cpp` never calls `llvm::DIBuilder` itself. The GIR side is the scope tree of a function (`Function::Scopes`, `docs/design/gir.md` section 14).

## 1. What it makes

- The compile unit (DWARF 5, `DW_LANG_C11`, `isOptimized` above `opt 0`, no `.debug_names`: gdb ignores an index it did not write and warns, and LLVM 23 leaves the base types of typed expressions out of it, which `llvm-dwarfdump --verify` reports), the files, the module flags.
- One `DISubprogram` per function with a body, on first ask (an inlined callee may be lowered later). `DW_AT_name` is `sym::demangle` of the symbol (`main.Vec2.+(main.Vec2)`); `DW_AT_linkage_name` only with the hidden `-dwarf-linkage-names` (section 4). Code the compiler wrote is `DW_AT_artificial`: the runtime and glue, which have no source position, and the wrappers (appendix A.5), which have the position of what they wrap: an interface thunk is at its method's declaration line, on the subprogram and on its instructions, so its frame shows that line whether the method is inlined into it or not (`debug/thunks.test`). Code with no position is line 0 throughout; gdb skips a row of line 0 and would read the row before it, the last line of the function before, so that code lies in a section of its own (`.text.gopp_nosource`, `DebugInfoBuilder::NoSourceSection`; the linker joins it to `.text`), a line sequence of its own: gdb shows no line for it, lldb line 0, never another function's (review R8). Above `opt 0` a subprogram says it is optimized. A Go++ function's type carries its calling convention, `DW_CC_LLVM_Swift` (P04.18, ADR-0030: swiftcc on every target); a C function (`@Extern`, `@Export("C")`, a thunk, `main`) carries none (`debug/place.test`). Neither debugger uses it for a return value (review R13): `finish` reads a result by the SysV rules, which agree with swiftcc for one and two words only. Measured on amd64 at opt 0:

| Result | Words | Where swiftcc puts it on amd64 | gdb 17 `finish` | lldb 22 `finish` |
|---|---|---|---|---|
| `int` | 1 | rax | right | right |
| `(int, int)` | 2 | rax, rdx | right | right |
| `(int, error)`, `(int, int, int)` | 3 | rax, rdx, rcx | "Cannot access memory at address 0x6" (reads rax as the address of a SysV memory result) | zeros |
| `(string, int)` | 4 | rax, rdx, rcx, r8 | garbage | garbage |
| `(string, error)` | 5 | memory (the hidden pointer) | right at opt 0 | right at opt 0 |

`DW_CC_nocall` makes gdb refuse every result (also the right ones) and lldb ignores it, so it is not used. TODO P14.07 (the debugger plugin) makes `finish` right; arm64 is not measured.
- The scopes of a function. A block of the source (`DebugScope::Block`) that holds a variable is a `DILexicalBlock`; one without is its nearest enclosing one. So shadowed names are distinct (an `x` of a block hides the function's `x` there) and a loop's `i` is gone after the loop. At most 64 blocks nest (`MaxBlockDepth`): LLVM walks the chain of scopes for each location and each variable (its verifier, and its passes above `opt 0`), so the work grows with the depth times the length. The parser allows about 500 nested blocks, but a cap that high was measured too slow: a function 490 blocks deep with 20000 statements in the deepest one spent 46 s in LLVM's `opt 2` passes with the cap at 512, 7.4 s with it at 64 (0.6 s against 0.2 s with 4 statements per block). A deeper block's variables are in the 64th block, which the blocks below it share. There a variable whose name another variable of the function has has no location: the debugger says `<optimized out>` (lldb: no location), never the value of another variable of that name, which it could not tell apart in the shared block; a variable with a name of its own is still shown (`DebugInfoStress.PastTheBlockLimitASharedNameHasNoLocation`, `debug/deep-scopes.test`). An inline site (`DebugScope::Inlined`, made by GIR inlining) is the callee's subprogram with an `inlinedAt` location at the call, in the scope of the call (a chain of inlining is a chain of `inlinedAt`); the callee's blocks copied below it are the callee's own `DILexicalBlock`s. Each site has its own distinct `inlinedAt`, as LLVM's inliner makes them: two inlined calls on one line are two frames.
- The `DILocation` of each statement and terminator, in its scope. A span of another file than the one of the scope's function is line 0, so the line table of a scope has the lines of its own file only.
- One `DILocalVariable` per local with `Local::Source` (a parameter, variable, named result or range variable of the program; compiler temporaries and the helpers' locals never have it, V011), in the scope it is declared in, `AlwaysPreserve`, declared at the local's slot with `dbg.declare`. Parameters are `arg:` variables. The copy that GIR inlining made of a callee's local is that callee's variable (`Local::Origin`; one variable for all copies, as LLVM's inliner shares them), in the inline site; the callee decides all of it, whether it is a variable too, never the function it was inlined into: a method inlined into its interface thunk, which has no position, keeps its receiver and locals (`debug/thunk-inline.test`, review R5). An aggregate parameter is the address the caller passed: a slot of its own holds it and the variable is read through it (`DW_OP_deref`), as Clang does for an indirect argument (a `move []T` too). A borrowed `[]T` parameter arrives as a `(ptr, len)` pair (P04.25) that the body makes into a slice of its own: that slice is the variable, shown as the parameter (`Local::ArgNo`), and the pair is no variable, so `info args` and `info locals` show `xs` once (`debug/borrowed-slice.test`). A parameter passed by a hidden pointer to the caller's place (P04.18, PAR-10: a borrowed map, a borrowed struct, array or Option that holds a string, slice or map, a value receiver that does) and a `&` range variable (RNG-1a) are described as the place they point to (`Local::Deref`: the pointee's type, read through the slot with `DW_OP_deref`), so `d` prints as the struct and `m` as the map (`m->count` is its length), while a plain pointer parameter `p *T` prints as the pointer (`debug/place.test`). A borrowed string is a `(ptr, len)` pair like a borrowed `[]T`, made into a string of its own with capacity 0, which is the variable.
- One `DIGlobalVariable` per writable package variable (`DW_AT_name` `main.counter`, so `print 'main.counter'` in gdb and `target variable main.counter` in lldb). Read-only constant data and the compiler's own variables (the map seed of the runtime: no position) have none.

## 2. Types: the one mapping point

`typeOf(const gir::Type*)` is the only function from a GIR type to a `DIType`. Later tasks add a case in `build()` and nothing else:

| Task | Adds |
|---|---|
| P04.06 | done when P04.12 was rebased on it: an interface value (`gopp.iface`) is `{itab, data}`, two addresses (`debug/iface.test`); thunks have no source position, so they are artificial |
| P04.07 (done) | a func value is the struct `{code, env}` named like its Go type (`func(int64) int64`; `env` an address); a closure is a function of its own named `main.f.func1` (its place in the enclosing function, from 1) and shows each captured variable by its source name, through the pointer in its environment (`Local::Deref`); its body is a lexical block of its own, so a local that shadows a captured name is the one shown; a parameter or named result an escaping closure captures lives in a cell whose pointer is set to the variable's own slot in the entry (`Statement::Prologue`) and to the cell after it, so it is right at `break f` too (`debug/closure.test` in gdb and lldb, `closure-arm64.test` in gdb under QEMU). Defer frames: P04.26 |
| P04.08 | generic instance names (`Name[args]` in `spell`) |
| P04.22 | `extends` parent as the first member (inheritance) |
| P04.24 | units: erased (D4.20), the display form goes in the name |
| P14 | pretty-printer scripts over these names |

Shapes today: ints and floats as `DW_ATE_*` (uint8 is `unsigned_char` so a string's data pointer prints its text); a string is a struct `{ptr, len, cap}` named `string`, a slice one `{ptr, len, cap, alloc}` named `[]T` (32 bytes, ADR-0029; the members are the GIR type's own fields, `Type::fieldType`); an array is `[N]T`; a struct is `main.Doc` with its field names (`Type::fieldName`, set by `lowerStruct`: a side table, not part of the type's identity, written in the bitstream so a body read back keeps them); an unnamed struct is spelled by its fields (`struct { a int64; b string }`); `Option(T)` is `{value, set}` and `Option[*T]` the pointer; a tuple has members `_0`..; a func is a pointer to a subroutine type; a map is a pointer to the runtime's `gopp.map` header, whose fields the runtime names (`count`, which is `len(m)`, ..., `alloc`, its allocator: null for the global one); an interface value is its two words `{itab, data}` as addresses (the data word holds a value of up to a word, or the address of one; as GIR's byte pointers a debugger would print text there); units are erased with their base type (D4.20). A self-naming type (`type S []S`) is named after the type with its body's kind; one that is a cycle of pointers and arrays only (`type L [1]*L`, `type O Option[*O]`) is a struct of its name with the body as its one member `value`, so that a declaration of the name finds a struct.

Names. A name stands for one layout, so a debugger that finds the definition of a declaration by its name finds the right one: a named type is its GIR name (unique: a second local type of one name keeps the lowering's `#2`); two unnamed structs of one spelling (`struct { a int }` and `struct { a int64 }`) have one layout and are one DWARF type; a name longer than 200 bytes (`MaxNameLength`) is cut and ends in `...#H`, H the 64-bit xxh3 hash of the whole type made from its parts' hashes, so two types that differ only past the cut have two names, and a type has the same name whichever type is spelled first (without the cut, a chain of N nested types has names of N levels: quadratic).

Pointers, cycles and height. A type is made once (bottom up, on `DeepWalk` stacks, so a chain of 20000 types needs no more stack than one) and is at most about 48 levels high (`MaxTypeHeight`, counting the members, pointers, elements and subroutine types that LLVM's DWARF writer recurses through, once per level; a struct that holds a chain adds two). What a pointer refers to (`target`, also a function type's parameters and result) is: for a struct-shaped type (a struct, string, slice, `Option`, tuple, or a self-naming pointer or array) the declaration of its name, a leaf, and the unit keeps the definition (`retainedTypes`, in the order of the names), where gdb and lldb find it by the name (`p *n.next`, `p->Pages`); for a pointer, a function or a scalar its definition; for an array the array of what its element is there. A cycle of types passes through a pointer or a function to a struct or a self-naming type, so the definitions refer to each other without a cycle. A part that lies inside a type (a member, an element) higher than the limit is referred to the same way: a struct by its declaration, an array of a high struct as the array of the struct's declaration. A chain of pointers, arrays and functions with no struct in it (`type P2 *P1`, ...) is held, every 47 levels, by a struct of its name with one member `value`, referred to by its declaration. So a pointer or an array is never a declaration itself: a debugger dereferences and indexes it (`debug/type-cuts.test`). Every choice depends on the type alone, never on which type was asked for first: asked for in any order, every type is the same DWARF, part by part (`DebugInfo.TypesDoNotDependOnTheOrderTheyAreAskedFor`), and the work is linear: a DAG of types with 2^N paths (`DebugInfoStress.ADiamondLadderOfTypesIsLinear`), a cycle of 4000 types, and chains of pointers, arrays and structs asked for from either end (`DebugInfoStress.ChainsOfPointersAndArraysAreLinear`). GIR does not tell `int` from `int64`, or `byte` from `uint8`, so a type is spelled by width and sign (`int64`); lldb spells an int64 `long` and an array without a name. Known limit (review R6): GIR gives two defined types over one underlying struct (`type Q0 T0`) one struct, named after the type lowered first (`lowerStruct`: a conversion between them is no code), so DWARF names both by that one name and the debugger shows a `T0` local as `main.Q0`; a name per use, written as a `DW_TAG_typedef`, is TODO P14.07.

## 3. Variables at every `opt`

At `opt 0` the curated pipeline runs SROA and instcombine, which would turn a variable into values that end at their last use (`<optimized out>` later), drop a store that the next one overwrites, and lose a global's address or `null` (no DWARF fragment form). So `LowerToLLVMOptions::KeepVariables` (set by `gopp build` and the fast runner for `opt 0`, not for `-pipeline=fastisel`, which runs no pass) makes every load and store of a variable's slot volatile, and every memset and memcpy that writes it (`Lowering::keepInMemory`): the passes leave the variable as the code wrote it, and the debugger prints, at any line, what the statements before it left. A memcpy out of a variable only reads it and stays plain, so it pins no temporary. The copies of an inlined callee's variables of more than 4 KB (`MaxKeptBits`) are not kept: 40 inlined calls with a 512 KB parameter must not be 40 frame slots (`run/core-argslots.test`); such a copy may print `<optimized out>` in the inlined frame, never a wrong value.

Why volatile (manager decision M2 of the team build; the numbers are geometric means over the 238 programs of the run corpus at `opt 0` with DWARF against `opt 0` without, on the coders' builds, under load). Leaving SROA and instcombine out of `opt 0` with DWARF (another coder's way) gave 2.40 times the text, 5.57 times the frame size, 1.08 times the compile CPU and 1.08 times the run CPU; it needed inlined callees to share aggregate slots, which changed the `-no-debug` code too (the frame of `core-argslots` grew from 72 bytes to 4.7 MB). Volatile accesses gave 1.18, 1.24, 1.06 and 1.02, and change nothing without DWARF. Volatile only says that an access must happen as written, which is true of every access, so no pass can use it to change what a program does. Pinning the slot with `llvm.invariant.start` (the third way) was rejected: it tells LLVM the memory does not change, which is false for a mutable variable.

At `opt 1` and up nothing is volatile: LLVM's passes promote the slot, `dbg.declare` becomes `dbg.value`s, and a variable has a location where its value lives and is `<optimized out>` elsewhere, never a wrong value (`debug/gdb-optimized-out.long.test`). The records cost: LLVM keeps one per variable and inlined frame, so a chain of 2500 functions each inlined into the next (3.1 million inlined frames) compiles at `opt 2` in 30 s and 3.9 GB, against 8 s and 1.6 GB with the line tables alone, and a block with 10000 variables spends 1.4 s in EarlyCSE, quadratic, as `clang -O2 -g` does on the same program in C (LLVM's own behavior); the numbers and what would close the gap are TODO P14.07, and `debug/inline-chain-vmem.long.test` bounds the memory.

The entry and `break f`. gdb and lldb stop at `break f` (and at a breakpoint on the declaration line) where LLVM puts `prologue_end`: the first instruction after the frame setup that has a line other than 0. The code that puts each parameter where its variable says it is has no line, as in Clang: the entry block (the stores into the slots, the slot of an aggregate's address, the words of an aggregate in registers) and the statements of the function's entry in GIR (`Statement::Prologue`: the variable a borrowed string or `[]T` pair is made into, the zero value of a named result, a closure's pointers to its captured variables, P04.07). A parameter or named result that an escaping closure captures moves into a heap cell, which takes a call, so it cannot be in the entry: its variable is the cell's pointer (`Local::Deref`), set to the variable's own slot in the entry and to the cell after it, so the debugger reads the right value on both sides of the move. The code that makes the cells is on the first line of the body (`Body::enterCells`): LLVM ends its search for `prologue_end` at a call and, finding no line before it, would put `prologue_end` on that call with the declaration's line; on the body's first line, `break f` stops there as for any other function (`debug/closure.test`, `main.scaled`, gdb and lldb, and gdb on arm64). So it lies in the row of the declaration line that LLVM starts the function with, and `prologue_end` is on the first line of the body, where every parameter is in its slot. With a line of its own (the declaration line, as before) the stores were the first instruction with a line and the debuggers stopped before them: `one(20)` showed `a=16`. GIR inlining makes the copy of a callee's entry the call's (its position and scope), as the copies of the arguments are, so the inlined frame, where a debugger stops at `break callee`, starts with every parameter set. `step` into a function is the other way in. lldb stops at `prologue_end` there too. gdb asks the target's prologue analyser: on arm64 it trusts the line table (the end of the declaration line's row, which is `prologue_end`); on amd64 it trusts the line table only for a producer that starts with `clang ` (`amd64_skip_prologue`, `producer_is_llvm` in gdb 17), which the producer `gopp` is not and must not pretend to be (gdb 17 also keys its amd64 epilogue unwinder, `amd64_stack_frame_destroyed_p`, and Clang's macro quirks on the producer), and else looks for `push %rbp; mov %rsp,%rbp`. Without a frame pointer it stopped at the first instruction, at the declaration line before the stores (`main.one (a=0)`). So unoptimized code with DWARF keeps the frame pointer (`"frame-pointer"="all"`, as Clang's `-O0`): gdb finds the frame setup and goes on to the end of the declaration line's row, the first line of the body. It costs two instructions a function and only there; `-no-debug` code and code above `opt 0` are unchanged. Every kind of parameter, receiver and inlined copy, at `break f` and at `step`, in gdb and lldb on amd64 and in gdb on arm64 under QEMU (`debug/params-break*.test`), and the line table on both targets (`params-break-lines.test`).

Known limit: a variable is visible in its whole block, also before the statement that declares it has run (`r := f()` while `f` runs); its slot then holds whatever was there, as in C.

## 4. Names in backtraces, the language

`DW_AT_name` of a function is the readable form. `DW_AT_linkage_name` (the `_GP` symbol, as the P04 README D4.7/D4.13 and appendix A.9 planned) is written only with the hidden `-dwarf-linkage-names` (`LowerToLLVMOptions::DwarfLinkageNames`; manager decision M3): gdb 17 and lldb 22 show a linkage name that is not an Itanium one in place of `DW_AT_name` and cannot demangle `_GP`, so every backtrace would read `_GPF4mainE4main`. The ELF symbol stays `_GP…` (nm, perf, `gopp demangle`). Bringing the linkage name back needs a debugger that demangles `_GP` (P14.07, both sides in the TODO).

The language is `DW_LANG_C11` (manager decision M4): gdb and lldb both have a type system and an expression parser for it (lldb has none for `DW_LANG_Go`), and with no linkage name both show `DW_AT_name`. C++14 was not needed: the debugger tests pass with C11.

## 5. The debuggers (manager decision M5)

The flake has gdb 17 (`pkgs.gdb`) and lldb 22 (`pkgs.llvmPackages_22.lldb`): new dependencies, for the debugger tests the task asks for in both debuggers. lldb is 22 because nixpkgs' lldb 23 does not build (a patch hunk fails); 22 comes from the binary cache and reads LLVM 23's DWARF 5. The alternative is lldb 23 built from source (a full LLVM build).
