# GIR: the Go++ mid-level IR

Task P04.01 · decisions D4.1 to D4.5, D4.15 to D4.20 of `plans/2026-10-27-goplusplus-language/04-gir-and-llvm-codegen/README.md`.

GIR sits between the checked AST and LLVM IR. It is shaped like Rust's MIR and Swift's SIL: typed, a control-flow graph of basic blocks, values in *places*, computed by *rvalues*, and **not SSA** (LLVM's `mem2reg` and SROA build SSA). This document is the contract for P04.04 to P04.24: every later task adds to a part named here and says which. The code is `compiler/lib/GIR` and `compiler/include/gopp/GIR`.

## 1. Where GIR sits

```text
 sema::CheckedPackage (AST + sema::Info)
        |  gir::lowerPackage        Lower.cpp   reads Info, never re-derives
        v
   gir::Module  --verify-->  per-function passes (sections 7, 8)  --> CodeGen
        |                                                          (LLVM IR)
        +-- gir::writeModule / readModule   (bitstream, section 13; .gopx)
        +-- gir::print                      (text, `gopp build -emit=gir`)
```

Rules that keep the layers apart:

- **GIR does not include LLVM IR, Clang or LLD headers.** `tools/check-frontend-includes.sh` checks it (GIR may include `llvm/ADT`, `llvm/Support` and `llvm/Bitstream`). Only `CodeGen` knows LLVM. The macro interpreter (P09) runs GIR, so GIR must stand alone.
- **The builder reads the checker, it does not decide again.** The type of an expression is `Info::typeOf`, a constant is `TypeAndValue::Val`, what a name denotes is `Info::Uses` / `Defs`. Nothing in `Lower.cpp` looks a name up or works out a type. If a later task needs a fact the checker does not record, the fact is added to `Info` (P03 style), not guessed in GIR.
- **One way to make a body:** `gir::FuncBuilder` (`Builder.h`). It computes the type of every rvalue, so types are made in one place; the verifier checks them again.

## 2. Data structures

All in `GIR.h`. Everything inside a body refers to its parts by **index** (`LocalId`, `BlockId`, `FuncId`, string id), never by pointer, so a body can be copied, substituted, serialized and compared. The only pointers are `gir::Type*`, uniqued in a `gir::Context`.

```text
Module      Ctx, Name (package path), Files[], Strings[], Funcs[], Globals[]
Function    Name (symbol), Sig (a Func type), Link, CC, NoUnwind, Loc
            Locals[] (0 = return place, 1..N = parameters, then the rest)
            Blocks[] (0 = entry; empty = a declaration)
            Scopes[]: the debug scopes, a tree (P04.12, section 14)
Local       Kind (Return, Arg, Var, Temp), Ty, Name, Mutable, Owned, Loc
            Source (declared by the program), Scope, ArgNo, Origin (P04.12)
BasicBlock  Stmts[], Term, Cleanup
Statement   Assign(Dest place, Rvalue) | StorageLive(L) | StorageDead(L) | Nop
            Boundary: a copy made by GIR inlining (never read from a file)
            Scope: the debug scope it is in (P04.12)
Terminator  Goto | Switch | Return | Unreachable | Call | Drop | Assert | Resume
            Scope, as a statement's
DebugScope  Block (a `{}` of the source) | Inlined (an inline site: Callee at Loc)
            Parent (an earlier scope; 0 = the function), Loc, Callee, Origin
Span        {File+1, Line, Col}: self-contained, needs no SourceManager (D4.7)
```

Design points:

- **Locals are stack slots, not values.** A `Local` may be assigned many times. LLVM turns the slots into SSA (`alloca` + `mem2reg`). GIR never needs phi nodes.
- **Temporaries** (`Local::Temp`) hold intermediate results. M0 gives them no `StorageLive` / `StorageDead`; P04.04 adds both where lifetimes matter (LLVM lifetime markers), and drop elaboration needs them for temporaries that own something.
- **`StorageLive` / `StorageDead`** mark the extent of a source variable. The builder keeps a scope stack; leaving a scope by falling out, `return`, `break` or `continue` emits `StorageDead` for exactly the locals of the scopes it crosses, innermost first (`Body::exitScopes`). This is also the shape drop elaboration needs: the *same* exits are where drops go (section 7).
- **Functions are separate objects with symbols as names.** A call names its callee as an operand (`Constant::Func`, or a pointer in a place for an indirect call). `Function::Name` is the final symbol; P04.17 owns how it is made. One function decides every name, `gir::symbolOf(SymbolKind, Package, Name)` (`Lower.h`): M0 makes `main.f` for package main, `<path>.f` for another package (`command-line-arguments` for files on the command line, as in Go), the bare C name for `@Extern("C")`, `main` for the C entry point and `gopp.<name>` for the compiler's helpers. A Go++ symbol always has a dot, so it never collides with a C name. P04.17 plugs its mangling into that one function.
- **`NoUnwind` and `NoReturn`** are on the `Function`. A call of a `NoReturn` function may have no return target (`Target == NoId`); the verifier checks that only such calls have none (V028).
- **Calling convention** (`CallConv`): `Go` is the internal convention (P04.18: `swiftcc` on both targets, chosen by the code generator for the target, ADR-0030; results in registers, `docs/design/calling-convention.md`), `C` the exact C ABI (D4.4, P04.11, `docs/design/c-abi.md`). It is part of a function type (`Func` types carry it, printed `fn "C"(...)` for C), and a function's `CC` is its signature's (V075), so a direct call takes it from the callee and a call through a pointer from the pointer's type: an allocator's table entry is a C function pointer and is called with the C ABI, the hash of a map's key type a Go++ one. A Go++ function reaches C only through a C-ABI thunk (P04.18), and a C function pointer is called by Go++ with scalars only until P04.07 (V074).

`Type.h`. GIR has its own types: fixed width (`int` is already `i64`), no names except structs, cheap to serialize and to substitute.

| `Float(bits)` | 32, 64 | `float32`, `float64` |

A type the lowering cannot map yet is reported with `err_gir_unsupported` (E0439), naming the construct, at its position. Nothing is silently dropped: what a refused method call, interface conversion or type assertion gives is a zero of its own shape (`Body::zeroOfExpr`; a tuple where several values are taken, an interface where one is), so the code that uses it reports nothing more, and every way out of an expression that could not be lowered goes through `Body::failed` (`errorValue`, `errorAt`), which reports an internal error (E0440, "a fact of the checker is missing") when nothing was reported before, so a missing fact never becomes a wrong value (P04.06 review R1, R6).

`Context` uniques structural types in a `FoldingSet` behind one lock. Types are the same type exactly when the pointers are equal. Nothing a type prints or serializes as depends on the order types were created in, so a context shared by threads that build different functions is deterministic in what it writes.

## 4. Places

A `Place` is a local plus projections; every projection records the type after it, so a place has a type without walking.

| Projection | Meaning |
|---|---|
| `Deref` | `*p`; the operand is a `Ptr` |
| `Field N` | field `N` of a `String`, `Slice`, `Tuple` or `Struct` |
| `Index _L` | element of an `Array` or a `Slice`, or a byte (`u8`) of a `String` (P04.05); `_L` is an integer local. **No bounds check here:** the check is an `Assert` before it (P04.04) |
| `ConstIndex N` | element `N` of an `Array` |
| `Downcast N` | the payload of variant `N` (enum-like `Option[T]`, interface data, `extends` parts); verifier rejects it until P04.04/05 define the types |

A **move path** (section 7) is a place with only `Field` / `Deref` / `ConstIndex` steps. Places with `Index` of a non-constant local are never move paths: moving out of an indexed element is not allowed for owning types (the checker already rejects it).

## 5. Operands, constants, rvalues

`Operand = Copy(place) | Move(place) | Const`.

- `Copy` reads and leaves the value valid. `Move` reads and leaves the source moved-from: elaboration zeroes it (Go++ values, D4.2 step 3) or marks it moved-from (C++ values: a move constructor call, P01 D1.4 rule 9). The builder emits `Copy` for trivial types and for borrows; `Move` for `move(x)` and for the implicit moves the checker decided. M0 has only trivially copyable values, so it emits `Copy`.
- `Constant`: `Int` (bits truncated to the type's width), `Float` (the bits of a double; an `f32` is rounded first), `Bool`, `Str` (an id in `Module::Strings`), `Func` (a `FuncId`), `Null`, `Zero` (all-zero value of any type), and `Global` (P04.04: the address of a package variable, `Bits` the global's index in `Module::Globals`, the type a pointer to its type; a place reaches the variable by a `Deref` of a temporary that holds it, so places stay local-based).

`Rvalue` kinds: `Use`, `AddrOf(place, mut)`, `Binary(op, a, b)`, `Unary(op, a)`, `Cast(kind, a)`, `Aggregate(kind, ops)` (tuple, array, string, slice, struct), `Len(place)`.

Operations carry **Go semantics, not LLVM semantics** (D4.12). The codegen of the operation, not the builder, implements the Go result:

- `Div` / `Rem` of signed integers: `MinInt / -1` is `MinInt`, `% -1` is 0. `Div` and `Rem` assume the divisor is not zero: the builder puts an `Assert(divisor != 0, DivByZero)` before them unless the divisor is a constant.
- `Shl` / `Shr`: a count `>=` the width gives 0 (or the sign fill for `Shr` of a signed value). A signed count is checked `>= 0` by an `Assert(NegativeShift)`.
- `Cast(FloatToInt)` saturates (`llvm.fptosi.sat`).
- `Add`, `Sub`, `Mul`, `Neg` wrap (two's complement); no `nsw` or `nuw`.

Comparisons produce `bool`. `Eq`/`Ne` are defined for scalars; strings, structs, arrays, `Option` and interface equality are calls or expansions made by P04.05, 06, 04 (they are not rvalues): P04.04 compares a struct, an array, a complex number or an `Option(T)` with a call of the type's eq glue (`gir::addEqGlue`, `Glue.h`, the one place that decides `==` and the hash of a type; `LinkOnceODR`, named by `sym::SemaNames`).

## 6. Terminators, unwind and cleanup

```text
Goto(T)                                 Switch(op, [(v, T)...], otherwise)
Return                                  Unreachable
Call(callee, args, dest, T, unwind)     Drop(place, T, unwind)
Assert(cond, expected, kind, T, unwind) Resume
```

- `if` is a `Switch` on a bool (`case 0` is the else edge). `switch` statements and type switches are `Switch` on an integer or on a tag read from an interface.
- **Calls and unwinding (D4.6).** Every terminator that can run user code (`Call`, `Drop`, `Assert`) has an `UnwindAction`:
  - `Continue`: no cleanup in this function, keep unwinding. LLVM `call`.
  - `Cleanup(B)`: run cleanup block `B`, which ends in `Resume`. LLVM `invoke` with `B` as the landing pad.
  - `Terminate`: a panic here aborts (a drop that panics while unwinding).
  - `Unreachable`: the callee cannot unwind (`NoUnwind`; every C function that is not `@Unwind`). LLVM `call nounwind`.
- **Cleanup blocks** (`BasicBlock::Cleanup`) run only on the unwind path. The verifier enforces: normal edges stay among normal blocks or among cleanup blocks (V023); a cleanup block is entered only by `Cleanup` unwind edges (V024); it ends in `Resume`, `Unreachable`, or an edge to another cleanup block, never `Return` (V025); a call, drop or assert in a cleanup block has the action `Terminate` or `Unreachable`, never `Continue` or `Cleanup` (V025: a panic during unwinding terminates, as in C++; the cleanup region cannot re-enter itself through an unwind edge, as in Rust's MIR). A `NoUnwind` function has no `Resume` and no `Continue` action; a direct call of a `NoUnwind` callee has no cleanup edge, and `Unreachable` (lowered as a `nounwind` call) is allowed only on a direct call of a `NoUnwind` callee (V026).
- **Catch blocks** (`BasicBlock::Catch`, which implies `Cleanup`) are the one cleanup kind that may leave the unwind path. They are the catch-all handler of a function with `defer` (D4.6): the deferred calls run inside it, and `recover` is a runtime call whose result a `Switch` tests. The verifier lets a catch block (a) `Return`, or branch to a normal block, after a recovered panic; and (b) make calls, drops and asserts that unwind onward (`Continue`, or `Cleanup` into a drop pad), because a deferred call that panics again replaces the panic (P01 D1.9). It still ends in `Resume` when the panic was not recovered. Only a catch block may branch into a catch block (V023), so normal code cannot fall into a handler; a catch block is also marked `Cleanup` (V024), so unwind edges name it like any pad. Plain drop pads keep the strict rules (V023, V025). The text dump prints `bbN (catch)`, the bitstream stores `BLOCK[cleanup, catch]` (magic byte `0xB2`).
- **How P04.07 uses it with ADR-0028's pad.** A function with `defer` keeps ADR-0028's single state-indexed landing pad: that pad is the catch block (`Catch`), entered by every `Cleanup` unwind edge. Each unwinding site stores its cleanup-state index into a slot before the call, and the catch block dispatches on it. GIR writes the dispatch as a `Switch`; the LLVM lowering of P04.07 turns it into compares (FastISel cannot select a `switch`, ADR-0028 Table 6). The chain below the dispatch runs the block-scoped drops of the state, innermost first; then the deferred calls LIFO, each a `Call` whose unwind is `Continue` or a `Cleanup` edge to a plain drop pad of the function-scope locals; then `recover`; then a `Switch` on "recovered": the recovered side drops the function-scope and defer-extended locals and `Return`s (or branches to the normal return block), the other side `Resume`s. Functions without `defer` use plain cleanup blocks only; the split pass and the `nounwind` rule (V026) of ADR-0028 decision 3 are unchanged by this.
- **Code generation (M0).** `Continue` lowers to a plain `call`, `Unreachable` to a `nounwind` call. A `Cleanup` edge (an `invoke` with a landing pad), a catch block, `Terminate`, `Drop` and `Resume` are refused with the task named (P04.07, P04.09): lowering them as plain calls would change what a panic does.
- **Defer and panics (P04.07).** A function with `defer` has a catch-all landing pad (a cleanup block that ends in a call into the runtime and a `Switch` on "recovered"): GIR needs no new terminator, only the `Catch` block kind above. `recover` is a runtime call. Under `-panic=abort` drop elaboration makes no cleanup blocks, and calls get `Unreachable` unwind.
- **`!` (P04.10).** `f!(...)` lowers to a `Call` followed by a `Switch` on the error word; the failure edge returns the error (`BangKind::Return`), calls the panic helper (`Panic`), or sets the deferred error (`DeferSet`). `Info::Bangs` says which, per call.
- **Bounds, nil, overflow checks** are `Assert` terminators with an `AssertKind` and, in `Args`, the values the message shows (V065: a bounds check has the index, as `i64` or `u64`, and the length as `u64`). Each check fails to a block it shares with every check of its kind in the function (ADR-0028 rule 3.3; a bounds check of an unsigned index has its own, as its message prints the number unsigned): the failing edge stores its constant source position (`{file, line, col}` in read-only data) and its values into entry-block slots and branches there; the shared block makes the function's one call of the kind's runtime function. Until P04.07 that is the bootstrap panic of section 15 (no unwinding); P04.07 makes the call an `invoke` with ADR-0028's state-indexed pad, and the shape stays. A module without the runtime function (one built by hand) fails to `llvm.trap`.
- **`go` / `select` / channel operations** are calls into the runtime (P12); `select` is a call plus a `Switch` on the chosen case.

## 7. Moves, drops and drop elaboration (P04.09)

The builder (P04.04) emits **no drops**. It emits moves (`Move` operands), assignments, and the scope structure of section 2. A separate pass, *drop elaboration*, adds the drops. This keeps the builder simple and gives the ownership checks (section 8) one CFG to read.

**Input facts.** For every local whose type has drop glue (`Info`/type query: an owning pointer kind, a type with a `drop` method, an owning container, a struct containing one) the pass tracks **move paths**: the local and its fields reached by `Field` steps. A path has a *state* at each point: initialized, moved-out, maybe-initialized. The state is computed by a forward dataflow over the CFG (bit-vector per move path; linear in blocks × paths, paths per function are few).

**Output.** At each place a value goes out of scope the pass inserts, in order:

1. at normal scope exit (`StorageDead` points, including those inserted for `return`/`break`/`continue`): a `Drop(place)` for each path that is *initialized*, innermost scope first, locals in reverse declaration order;
2. for a path that is *maybe* initialized: a **drop flag**, a `bool` local set to true at initialization and false at a move; the drop is guarded by a `Switch` on the flag;
3. on every `Call`/`Drop`/`Assert` that can unwind: a chain of cleanup blocks that drops the paths initialized at that point, in the same order, then `Resume`. Calls whose live-droppable set is empty get `Continue`. Chains are shared between calls with the same set (the cleanup block for a set is made once).

**Rules it implements (D4.2 step 3).**

- Moving a Go++ value copies the bytes and **zeroes the source** (`Move` operand elaborated to a copy plus `Assign(zero)`); drop glue skips `drop` on an all-zero value.
- Moving a C++ value runs its move constructor (`Call`), leaves it moved-from, and destroys it at scope end (the Go++ and C++ distinction is a flag on the type, from `Info`).
- Defer-extended locals (D4.6): the local lives in the defer record; the scope-end drop is *not* emitted for it; the function-scope cleanup drops it after the deferred calls.
- A swap of places evaluates every index, key and pointer operand (with its bounds and nil checks) before it moves anything (OWN-R4): the builder lowers a parallel assignment to "evaluate all operands into temporaries, then store". M0 already does this for `a, b = b, a+b`.
- Drops of temporaries happen at the end of the statement that made them (Go++ has no extended temporaries).
- **Owned temporaries (P04.05).** The lowering marks the temporary that holds a value the runtime just allocated (a `+` result, a conversion, `make`, a literal, `map_new`, the pack of a variadic call) with `Local::Owned` (printed ` [owned]`, serialized, verifier V014: only a `Temp` may carry it). It is the list of drops P04.09 must make: drop the temporary at the end of the statement unless an operand `Move` took it. The `append` result is not marked: it is stored into the slice it grew, which is a variable the pass already tracks. Until P04.09 nothing is freed and every owned value leaks (section 15).

## 8. The ownership, borrow and concurrency checks (P04.09, P04.20, P04.21)

They run per function, after the builder and before drop elaboration, over **the GIR CFG**. A *point* is `(block, statement index)`; the terminator is the last point of the block. They read, besides GIR:

- `Info::Types`, `Uses` for borrow modes (`Var::Mode`: `Borrowed`, `Alias`, `MoveParam`), already decided by P03;
- the per-function summaries from export data (borrow summary, "writes this parameter", "callee keeps this parameter").

**What GIR must provide so they stay linear:**

- Every read and write of a variable is an operand or a destination **place**: a use of a move path is a point. No hidden uses.
- `AddrOf(place, mut)` is the only way to create a borrow, so each borrow has one creation point and a `mut` flag (D4.16 modes). `Call` operands that are references carry the borrow forward to the destination by the callee's borrow summary.
- Liveness of a borrow is the backward liveness of its destination local; a "change" of the borrowed place (an `Assign` to the place or a prefix, a `Move`, a `Drop`, a call that writes the parameter) at a point where the borrow is live is the error. Overlap is a path-prefix test with constant indexes and distinct fields known disjoint.
- `go` and `s.Go` are `Call` terminators to a runtime function whose closure operand records captures; the concurrency pass reads capture modes (moved, copied, shared) from the closure aggregate.
- Spans on every statement and terminator give the diagnostics their positions.

Each pass is one forward and one backward walk, linear in function size; each gets a generated stress test (the lessons in CLAUDE.md).

## 9. Verifier

`Verify.h`. It runs at the end of `lowerPackage` (an error is `err_gir_verify`, E0440, "internal error"), after every read of the bitstream (`readModule`), and at the start of `lowerToLLVM` (a module built by hand is checked too), so each test that makes GIR verifies it. It trusts nothing it is given and recomputes every type. Each rule is decided in one function of `Verify.cpp`, under its id. Every walk is iterative and the time is linear in the module: a place is a loop over its projections, the CFG a work list, the types a work list that looks at each type once, the struct-cycle check a three-colour DFS with its own stack (`tests/unit/GIR/StressTest.cpp`: 80000-block ladders, wide cleanup regions, thousands of functions; four times the input costs at most 4.5 times the counted steps in the normal suite, and at most 12 times the time in the long suite).

An error is `VerifyError{Rule, Func, Block, Index, Message}` and prints as `V027: fn main.f: bb3 #2: duplicate switch case 1` (`#` is the statement index; the terminator has index `Stmts.size()`). `verify(M, MaxErrors)` stops at MaxErrors.

| Rule | What is checked |
|---|---|
| V001 | every function exists and has a name no other function has (the name is the symbol) |
| V002 | type shapes: integers 8/16/32/64 bits, floats 32/64, a struct or `Rec` the module uses has its body, no part is missing |
| V003 | a struct or a `Rec` does not contain itself by value (through fields, arrays, tuples, `Option` payloads and the body of a `Rec`; a pointer, slice or string ends the walk) |
| V010 | the signature is a function type |
| V011 | local 0 is the return place of the result type, locals 1..N the parameters of the signature's types in order, every other local a variable or a temporary; every local has a type; `Local::Source` (declared by the program, for the debugger) only on a parameter or a variable |
| V012 | a declaration (no blocks) has no locals |
| V013 | the entry block is not a cleanup block and no edge goes back to it |
| V014 | `Local::Owned` is set only on a `Temp` (P04.05) |

## 10. Monomorphization (P04.08, D4.3)

- **Generic bodies are built once, with `Param` types**, in the package that declares them, and stored in export data (section 13). An instance is made by *substitution* on the GIR body: every `Type*` in locals, places, rvalues and constants is mapped through the type arguments, and every `Call` of a function with the generic's own `FuncId` and type arguments is redirected to the instance. Method calls on a type parameter are the `Info::Operators`/`Selections` entries marked `ViaConstraint`; after substitution they name the concrete method (the same function the plain code would call), so plain and generic code share one resolver.
- **Instance key** = origin function + the type arguments as *canonical GIR type strings* + target. Two instances with the same key are the same function. The key's text is the mangled suffix P04.17 appends to the origin's symbol.
- **Fingerprint** (debug builds, one home per instance across packages, D4.3) = hash of the instance's substituted GIR bytes (`writeModule` of just that function, deterministic) + the fingerprints of every type and function it references + the profile settings that affect codegen + target.
- **Per-instance checks** (`Option[X]` of a nilable `X`, `call[error]`) run at substitution, with the checker's own predicates, because the checker saw only the generic body (D4.3).
- **Unit dictionaries (GEN-14, P04.24).** A generic whose `TypeParamType::uses()` contains `UnitDict` takes one hidden parameter per unit parameter: a pointer to a descriptor `{factor: f64/rational bits, dimensionless: bool}`. The `Info::UnitSites` of the body (kinds `Mul`, `Quo`, `Conv`, `Const`) become `Binary` operations whose factor operand is loaded from the dictionary; the "factor where the unit is dimensionless at the instance, 1 elsewhere" rule is evaluated at substitution when the instance's units are known, so an instance with static units has no dictionary parameter left and the factor is a constant.
- **Hierarchy type tables (P04.22).** `extends` types with `@Virtual` / `@Abstract` methods get a table global: `Struct("pkg.T.vtable")` of function pointers in method order, plus the parent-table pointer and a depth for downcast checks. A virtual call is `Call` with an indirect callee (a `Field` of a loaded table). The table is emitted per type (`linkonce_odr` in release). `base.M()` and every non-virtual call are direct (`Selection::Base`, `ParentSteps` give the field path to the parent part: `Field 0` repeated).

## 12. Printer

`gopp build -emit=gir` (alias `-dump-gir`) and `gopp gir dump file.girb` print the same text. The text is for people and FileCheck, the bitstream is the data. Example (hello, shortened):

```text
module "command-line-arguments"
file 0 "hello.gopp"

declare fn write(_1: i32, _2: *u8, _3: u64) -> i64 [c, external, nounwind]

fn main.main() -> () [go, external] {
  let _0: ()
  let _1: string
  bb0:
    _1 = const str#0 "hello\0A"  ; hello.gopp:7:2
    _2 = call const fn @write(const 1: i32, copy _1.0, copy _1.1) -> [return: bb1, unwind: unreachable]
  bb1:
    return  ; hello.gopp:8:1
}
```

A function line ends with `[go|c, external|internal|linkonce_odr, nounwind, noreturn]` (the last two when set). The globals come before the functions, one line each: `global @sym: type`, with ` = const ...` for a static value (`constdata` for read-only data) and ` = { const ..., ... }` for static data (`Global::Parts`, P04.06: the leaves in order); an assert prints the values of its message after its kind (`assert(copy _5 == true, "Bounds", copy _3, const 3: u64)`).

Places print as `_1`, `_1.0`, `(*_1).2`, `_2[_3]`, `_2[0]`; blocks `bbN`, `bbN (cleanup)` or `bbN (catch)`; positions after `;` (`-gir-no-locs` leaves them out). Local and block numbering is the order of creation; dead blocks are removed and the rest renumbered in old order, so the numbering is stable for one input.

## 13. Serialization (D4.15)

`Serialize.h`. The container is **LLVM's bitstream** (`llvm/Bitstream`), used only as a container; `llvm-bcanalyzer` shows the block layout but cannot read the records.

```text
file      = magic "GIR" 0xB1 | IDENT block | MODULE block | index offset (u64 LE, 2 x 32 bits)
IDENT     (id 8)  : VERSION [chars]                 the Go++ version string
MODULE    (id 9)  : NAME [chars]
                    FILE [chars]            *        Module::Files in order
                    STRING [chars]          *        Module::Strings in order
                    TYPES block (id 10)
                    GLOBAL                  *        M_Global: name, type, initializer
                    GLOBAL_DATA             *        M_GlobalData: global index, then
                                                     (constKind, type, bits)* (Global::Parts,
                                                     after every GLOBAL; P04.06)
                    FUNC_DECL               *        one per function, in FuncId order
                    FUNC blocks (id 11)     *        one per function with a body
                    INDEX block (id 12)
TYPES     : one record per type, post-order (components before what they make
            up); then STRUCT_BODY and REC_BODY records. Codes: UNIT, BOOL,
            INT[bits,signed], FLOAT[bits], STRING, PTR[t], SLICE[t], ARRAY[t,len],
            TUPLE[t...], OPTION[t], FUNC[ret,fails,params...], STRUCT[name chars],
            STRUCT_BODY[id,n,fields...], STRUCT_FIELDS[id,n,(length, name
            chars) per field] (P04.12), REC[name chars] (a self-naming type, a
            leaf like a struct), REC_BODY[id,kind code,len,n,parts...]
FUNC_DECL : [sig, link, cc, nounwind, noreturn, file, line, col, name chars...]
FUNC      : BODY[funcId]; SCOPE[kind,parent,callee,origin,span(3)]*;
            LOCAL[kind,ty,mutable,owned,source,scope,argno,origin,span(3),name chars]*;
            then per block BLOCK[cleanup,catch], STMT[kind,span(3),scope,payload]*,
            TERM[kind,span(3),scope,payload]
INDEX     : BODY[funcId, bit offset low32, bit offset high32] *
```

- **Operands inside records** are flat `uint64` runs: a place is `local, nproj, (kind, val, type)*`; an operand is `kind, then (constKind, type, bits)` or a place; an rvalue is `kind, type, payload`. The reader recomputes nothing: a place's type is the last projection's type, or the local's.
- **Type ids** are assigned in the order the writer first meets a type walking the module (declarations, then bodies in order), components first (iteratively, so deep types cannot overflow the stack). Struct and `Rec` *bodies* are written after all types, so recursive structs and self-naming types are fine.
- **Index and jumping.** Every body is a block whose length is in its header. The trailer holds the bit offset of the INDEX block; the INDEX records hold the bit offset of each FUNC block. `ReadOptions::OnlyFunction` reads the tables and the declarations of all functions and the body of one (the others stay declarations): this is how P06 instantiates one generic or inlines one function without reading the whole file.
- **Version.** The IDENT block holds the compiler version; `readModule` fails with "rebuild" on any mismatch (the same compiler only, as in Go). There is no compatibility across versions, so records may change freely between releases.
- **Deterministic.** No pointer or hash order is written: the same module gives the same bytes (`GIRSerialize.RoundTripsAndIsDeterministic`, `tests/gir/roundtrip.test`).
- **Damaged input is an error, never a crash:** every id and enum value is range-checked, every record read is bounds-checked, a second body for one function is refused, and the module is verified after reading, so a source position that names no file (V070) never reaches the printer (`GIRSerialize.DamagedInputIsAnErrorNeverACrash` truncates and flips every byte, and prints each module that still verifies).
- **Text round trip.** D4.15 asks for binary to text to binary with identical bytes. The binary to text half exists (`gopp gir dump`, and the test requires its output to equal `-emit=gir`'s). A reader of the *text* form is not written: it is needed only for hand-written GIR tests, and P04.04 adds it if those tests want it. Until then the round trip is binary to module to binary (identical bytes) and binary to text equal to builder text.
- P06.02 puts these blocks into the `.gopx` sections; it needs a way to write several modules or one module with a part of its functions. `writeModule` takes a whole module; P06.02 may add an overload that writes a subset (functions by id). The format already allows it: the function records are self-contained apart from the module-level tables.

## 14. Debug information (D4.7, P04.12)

Each statement and terminator carries a `Span` (file index, line, column) and a **debug scope**. The code generator holds one `DebugInfoBuilder` (`CodeGen/DebugInfo.h`, `docs/design/debug-info.md`), which makes the compile unit, one `DISubprogram` per function (`DW_AT_name` is the readable form; the design note says why the linkage name is opt-in), the scopes, the `DILocation` of each statement, a `DILocalVariable` for each local the program declared, the globals, and the type of every value (`typeOf`, the single mapping from a GIR type).

**Scopes.** `Function::Scopes` is a tree below the function (`ScopeId` 0 is the function; N > 0 is `Scopes[N - 1]`, and a parent has a smaller id, so one pass in order sees every parent first). A scope is a `Block` (a `{}` of the source; the lowering opens one per scope of the source but the function's outermost, `Lowering::pushScope`) or `Inlined`: an inline site, the body of `Callee` that GIR inlining put into this function at the call at `Loc` (only `inlineTrivial` makes one; `pipelines.md` section 3). The callee's own blocks are copied below the site, each naming the callee's block it copies (`DebugScope::Origin`). `Local::Source` marks the locals the program declared (a parameter, variable, named result or range variable: the debugger's variables, V011); `Local::Scope` is the scope a variable is visible in; the inliner gives the copy of a callee's local the callee's id (`Local::Origin`; the debugger shows the callee's variable for all copies) and a parameter's position (`Local::ArgNo`). `ArgNo` also marks the variable that stands for a parameter: the slice the body makes of a borrowed `[]T` parameter's `(ptr, len)` pair (P04.25), which the debugger shows as that parameter. The printer shows them with `PrintOptions::Scopes` (off by default, so a dump is the same as before). Struct field names (`Type::fieldName`, `Context::setFieldNames`) are a side table: not part of a type's identity, so `Pair{a int}` and `Pair{b int}` of one name are still one type; only the lowering of a struct sets them, and the bitstream keeps them.

**Verifier.** V073 (the scope tree) and V074 (what names a scope), section 9. They make the code generator's walks safe on any module that verifies: every `Origin` names a block or a local of the callee's own, so the debug information of a copy is found in the callee's own scopes.

## 15. The subset built today and what each task adds

Built today (P04.04; `Lower.cpp` types, declarations, globals and init order; `LowerExpr.cpp` places, values, operators and checks; `LowerStmt.cpp` statements; `Runtime.cpp` the helpers the compiler writes in GIR; `Glue.cpp` `==` and the hash of a type; `Symbols.cpp` names; the decision points are listed in `LowerImpl.h`): package-level functions with parameters and results of every type below, several and named results (a bare `return`), recursion; `@Extern("C")` declarations; every integer width, `uintptr`, `float32`, `float64`, `complex64`, `complex128` (`Tuple(f, f)`; `real`, `imag`, `complex`, Go's `complex128div`), `bool`, and defined types over them; structs and arrays (types, zero values, positional and keyed literals, `Field`/`Index`/`ConstIndex` places as lvalues and rvalues, copies, `==`/`!=` through eq glue, `len`/`cap`); raw pointers (`&x` of locals, globals, fields and elements, `*p` read and written, `p.f` through a pointer, pointer `==`); `unsafe` (`Sizeof`, `Alignof`, `Offsetof` are checker constants; `unsafe.Pointer` to and from `*T` and `uintptr`, `unsafe.Add`); `Option[T]`; package variables and `init` functions; `if`, `for` in every form but `range`, expression `switch` (with and without a tag, an init statement, `fallthrough`, `default` anywhere; constant integer cases are one `Switch`, the others a chain of tests in source order), labels, `break`/`continue`/`goto`; every D4.12 conversion; `println`/`print` of every scalar in Go's format. Strings exist only as constants (cap 0): a string that is not a constant stored into a struct or an array would need drop glue and is E0439 naming P04.09, as is heap allocation (`new`, `&T{...}`, `Unique`, `Shared`); everything else outside the subset is one E0439 naming its task.

- **Layout (D4.5).** `Option[P]` of a raw pointer is the pointer (null is `nil`); any other `Option[T]` is `Option(T)`: the payload, then the flag. An `Option` of a `Unique`/`Shared`/`Weak` pointer or a func is refused (P05, P04.09, P04.07); an `Option[I]` of an interface with methods is the interface itself, its nil a null itab (P04.06, "Interfaces" below). The checker's `unsafe.Sizeof`/`Alignof`/`Offsetof` (`Sizes.cpp`) follow D4.5 for Go++ code (a string is 24 bytes, a func value 16, `Option[I]`/`Option[F]` the size of `I`/`F`, no gc padding byte after a trailing zero-size field; `CheckOptions::GoCompat` keeps gc's model for the Go conformance tests). `tests/unit/CodeGen/LayoutTest.cpp` checks every size, alignment and field offset of a generated table of 284 types against LLVM's data layout on both targets.
- **Aggregates in the code generator.** A string, slice, array, tuple, struct or `Option(T)` is never a first-class LLVM value: it is copied with `memmove`, zeroed with `memset` and built in place (V057), and the internal convention (P04.18, `docs/design/calling-convention.md`) passes it as its scalars when it has at most four and returns it in registers when its scalars fit the target's return registers (so a result of several values stays in registers); otherwise a parameter is a pointer to the callee's own copy and a result is written through a hidden first parameter into the caller's temporary (V066). A borrowed string or `[]T` parameter is `(ptr, len)`, a borrowed aggregate that holds an owning value is a pointer to the caller's place (PAR-1, PAR-10). The callee's copy of an aggregate argument lives in a slot of the caller's frame, one per (type, position among the aggregate arguments) shared by all the calls of the function (the copies of a call are dead when it returns, and the calls of a function run one after the other), so 40 calls that pass a 512 KB array use 1 MB of frame, not 20 MB (`run/core-argslots.test`). So a `[1 << 20]int64` global or a struct of 50000 elements passed by value compiles (`run/core-bigdata.test`).
- **Equality and hash glue (`Glue.h`).** Made from the GIR type alone, once per type (`LinkOnceODR`; a part of a type nested more than 24 levels deep, as in a chain of named types, is compared or hashed by a function of its own, `Internal`, so no function recurses per link and none has a place thousands of projections long; the part functions are built from a list, one after the other): integers, bools and pointers by value; floats as IEEE (`-0 == +0`, `NaN != NaN`; the hash maps both zeros to one value and every NaN to one value); structs, tuples and arrays part by part (a loop for an array longer than 4); `Option(T)` is "both nil, or both set and the payloads equal", and its flag padding and a nil one's payload never take part in `==` or the hash. P05's maps call the hash (`unit/CodeGen/OptionHashTest.cpp` runs it on the real layouts with garbage in the padding; `unit/GIR/GlueTest.cpp` on hand-made types).
- **Package variables and init.** `Module::Globals` (V071); code reaches one through `Constant::Global` and a `Deref`. A variable whose initializer is a scalar or string constant is static data; the others are set by the package's init function in the checker's order (`CheckedPackage::InitOrder`, entries `{Lhs, Init}`; `var a, b = f()` is one entry), which then calls the `init` functions in the order of the files as the checker was given them (a directory's sorted by name; `gopp build c.gopp a.gopp` runs c's first, as `go run` does) and, in a file, in source order. The C `main` calls the package init, then `main.main`.
- **Checks and the bootstrap panic (D4.12, ADR-0028 rule 3.3).** Division and remainder by a non-constant zero, a negative signed shift count and an array index out of range are `Assert`s (section 6); `MinInt / -1` and shifts at or above the width are no checks, the operations give Go's result (section 5). The shared block of a kind calls `gopp.panic_<kind>` (and `panic_Bounds_u` for an unsigned index), written in GIR by `Runtime.cpp` on top of C `write` and `exit`: it writes Go's first line to standard error (`panic: runtime error: integer divide by zero`, `negative shift amount`, `index out of range [5] with length 3`, a negative index without the length as Go does) and exits with status 2. There is no unwinding and no trace yet: P04.07 turns the call into an unwinding panic, P05 adds the stack trace.
- **Assignment order (Go spec, "Assignment statements").** Phase 1 evaluates the operands of index expressions and pointer indirections on the left (the implicit indirection of `q.x` too: the pointer is copied into a temporary) and the expressions on the right, in the usual order. Phase 2 stores left to right, and the index check of a target is part of its store: `x[1], x[3] = 4, 5` sets `x[1]`, then panics, and `a[n(5)] = f()` calls `f` before it panics. A target's pending checks (`Body::Pending`) are made just before its store; for `op=` the right side comes first, then the checks, then the read of the place (as gc). Each iteration of `for k, v = range x` is the assignment `k, v = key, value` (P04.05): the operands of both targets first, then the stores, so `for i, a[i] = range xs` indexes with the `i` of the iteration before, as `go run` does.
- **Late reads (P04.05 review R1, R2, R8).** A place into a container that later code of the statement may grow or move (a slice's buffer, a map's entries) is never kept across that code: every assignment target (`=`, a tuple, `op=`, `++`, a `range` clause), the slice `append` adds to, and the map passed to a borrowed map parameter is made in one way. `Body::recordOps` evaluates only its operands in phase 1 (index values, map keys, slice bounds, a value that is no place, such as a call) into temporaries; the place is lowered again later under `Body::ReplayScope`, where `lowerExpr` of a recorded operand is its temporary, so nothing is evaluated twice. A target is lowered again after the right sides and before the statement's first store (`Body::deriveDest`): the variables, slice headers and pointers along it are read then, as gc does (`xs[1] = grow()` writes the slice `grow` made; `s, s[0] = t, 50` still writes the old `s`, as the spec says), and an index whose element is read (a header, a pointer, the owner of a map) is checked before that read (as gc: `x[1], s[9][0] = 4, 5` panics before `x[1]` is set; an array in an array keeps both checks for the store). Its map entries are made at its own store (`Body::resolveDest`), outer to inner, from the map as it is then: `mm[a][b] = v` makes `a`'s entry, then `b`'s in that entry's map, so an earlier store of the statement that grows `mm` cannot leave a stale entry pointer. `append` reads its slice after its other arguments (EXP-3), and so does an in-place shrink `s = s[i:j]` after the other right sides of its statement (its bounds are evaluated in their turn); a borrowed map argument's address is taken after the other arguments. The move of an in-place shrink (SLC-7) runs after all the stores of its statement. Where Go's order is defined these agree with it (`run/core-latewrite.test` has Go's output); `g, x = g[1:], grow()` with `grow` appending to `g` keeps Go's old array in Go and shrinks the grown slice in Go++ (`run/core-latewrite-gopp.test`). P04.09 must keep this: a value a store replaces (`s` in `s, s[0] = t, 50`) is dropped after the statement's last store, not at its own, as a later target may still write into it.
- **A type that reaches itself (P04.05).** A defined type that reaches itself through a slice, a map, an array, a pointer or an `Option` and not through a struct is a `Rec` (section 3): `Lowering::recShell` hands out the type while its body is under way, so `type S []S`, `type M map[string]M`, `type O Option[*O]` and `type A [2]Option[*A]` lower and run. The type of a map's key and element is lowered without shells (`MapDepth`: the runtime sees only sizes and glue). What stays refused is a cycle through a function value (`type F func(F)`, P04.07), one E0439 naming the task (`tests/gir/recursive-refused.test`); a cycle through an interface (`type I interface{ M() I }`) lowers since P04.06, an interface being one GIR type for every interface; a null type without a report is an internal error (`unsupported`), so no function is left out silently.
- **FMA contraction (D4.12, manager decision M2; across statements P04.13).** gc fuses a float `x*y` with the `+`/`-` that reads it on arm64 and never on amd64. The code generator is the only place that decides, at every `opt` (`docs/design/pipelines.md` section 4): on arm64 it writes `llvm.fma` where gc fuses, and no float instruction carries `contract` or any other fast-math flag, so no LLVM pass or selector fuses anything else, and a float conversion needs no `llvm.arithmetic.fence` (a conversion is not a product to the matcher: `float64(x*y) + z` is not fused). Matched, as gc's SSA rewrite `FADDD a (FMULD x y)` does: a *product*, a local written by a float `*`, by the negation of a product, or by a copy of a product (the same SSA value in gc; `t := x*y` is `tmp = x*y; t = copy tmp` in GIR), that is a temporary read once (the value of a sub-expression) or a variable, parameter or result whose address is never taken (`AddrOf` of it anywhere in the function ends it). A variable read twice fuses at each `+`/`-`. Which write a read sees follows gc's SSA value: the blocks of a function with a float product are lowered in the preorder of the dominator tree and the products are scoped by it (an undo log), so a read sees the last product write of the local in its own block or in a block that dominates it, whatever order the blocks have in the function; across blocks, another write of the local that the product's block reaches and that reaches the read, without a path through the product's block again, makes it a phi, as in gc (the test numbers the strongly connected components of the CFG in topological order and sorts each local's writes by that number: one binary search per read, and one walk per variable and product block when the search finds a write in range; a walk enters only the blocks numbered up to the read's, so it covers the loop or region between product and read, not the rest of the function: 32 sibling loops each fuse, `Pipeline.EverySiblingLoopFuses`; the walks of a function share a budget linear in its size, and a read after it is spent is not fused, which takes very many variables that each need a walk over one large loop). The analysis is linear in the blocks, edges and writes (`Pipeline.TheFmaAnalysisIsNearLinear`, counted per dimension). Both operands products: the right one first, as gc's rules try them. The negation of a fused result is kept from LLVM's AArch64 FNMADD patterns, which give +0 where Go's `-t` is -0 (`FenceNegatedFmaPass`, pipelines.md section 4, review R8; `run/core-fma-neg.test`). Constant factors, as gc's generic rules see them before its FMA rules (generic.rules, "floating point optimizations"; `mulShape` in `LowerToLLVM.cpp`): `x*2` is `x+x` (no product, and the sum fuses a product x holds), `x*1` is x, `x*-1` is `-x`, `x/c` with c a power of two whose reciprocal is exact is the product `x*(1/c)`, `x*-2` stays a product, and an operation on two constants is folded (not when the result is NaN). A constant is a GIR constant or a float local whose one reaching write is a constant, a copy of one, a fold, or a conversion of one (from a float, or from a signed integer local written with a constant): `k := 2.0; x*k + z` and `j := k + k; x*j + z` are not fused, `x/2 + z` and `k := 2.0; x/k + z` are (`run/core-fma-vars.test`, mul2 ... constLocals, gc's goldens on both targets). A call, a bounds check or a division check ends a GIR block, so `x*y + f()`, `x*y + a[i]` and `a[i]*b[i] + c[i]` are fused (`run/core-fma.test`, `run/core-fma-vars.test`, both targets; a call of the runtime between them too, `run/core-fma-runtime.test`). The negation of a product is a product of the negated first factor (gc: `FNEGD (FMULD x y) => FNMULD x y`, then `FADDD a (FNMULD ..) => FMSUBD`, `FSUBD a (FNMULD ..) => FMADDD`, `FSUBD (FNMULD ..) a => FNMADDD`), so `-(x*y) + z`, `z - -(x*y)` and `-(x*y) - z` are fused too. Not products: a variable that two branches write (a phi in gc), a variable whose address is taken (not an SSA value in gc), the result or an argument of a call. GIR inlining keeps that: the copies it makes for the parameters and the result are marked `Statement::Boundary` and the matcher does not look through them, so `mul(x, y) + z` is fused in no pipeline (gc inlines `mul` and fuses; Go allows both, and the result of a program may not depend on `opt`). Against gc's arm64 output under QEMU: `run/core-fma-vars.test` and `Inputs/opt/fma-1..4` (random programs of `Inputs/gen-fma.py`; while P04.13 was merged, 120 seeds matched gc's arm64 output at `opt 0`, `opt 2` and `-pipeline=fastisel`, and 60 seeds its amd64 output). Not matched yet, each checked against gc (P04.14's TODO item): a product in a struct field or an array element, or in a variable whose address is taken but does not escape (gc keeps both in SSA values); a product that gc's prove pass leaves unwritten because it shows a branch dead (`if k < -1000 { goto A }` followed by `if k < -1001 { goto B }`: the second edge is a phi input here; the random CFG comparison missed 13 of 300 programs, all of this kind, and 0 of 300 with conditions gc cannot prove); a function where more variables need a walk than the budget pays for (very many variables written twice in one very large loop); both operands products (gc's choice follows its SSA value order, which the source does not decide; the differential table leaves those out); a constant gc's SSA knows and this does not, where gc applies a rule of the constant factors above and Go++ does not, so Go++ fuses where gc does not: phielim and sccp (a local written with the same constant on several paths, integer copies and arithmetic, unsigned conversions: `k := 2.0; if c { k = 2.0 }; x*k + z`), and memory and aggregates (review R9: a field of a small struct, an element of an array or slice literal, a value stored through a pointer and loaded back, the Load-of-Store rules of `generic.rules` 769-772; with 2 there `x*a[0] + z`, `x*s.k + z`, `x*(*p) + z` and `x*s[0] + z` print +Inf with gc and 1e308 here, and `a[0]*a[1] - 1` prints 0 with gc and -5.551115e-017 here); and a product across a call gc inlines.
- **GIR inlining and the pipelines (P04.13).** `gir::inlineTrivial` (`Inline.h`) inlines a direct call of a trivial function (one block, no call, no `Assert`, no `Drop`, no `AddrOf`, no owned temporary, at most 12 statements) in the `opt` pipelines and not in `-pipeline=fastisel`; a call with a `Cleanup` unwind edge is left. `docs/design/pipelines.md` has the pipeline table, the stages, and where profiles, `-trace`, LTO and the ADR-0028 split pass plug in. `Statement::Boundary` is the only GIR field it adds; no verifier rule changes (the inlined module satisfies the existing ones, `GIRInline.*`).
- **Symbols (P04.17).** `gir::symbolOf` and `gir::Symbols` name every function and global through `sym::SemaNames` and `sym::mangle`: `_GPF4mainE3add` is `main.add`; a package named main is `main` whatever path the command line gives it; `@Extern("C")` keeps its C name and the entry point is `main`; a type declared in a function gets the function and its ordinal there (`localNamed`), an `init` function its ordinal in the package (`initFunc`). The names depend on the source only (`gir/symbols.test`, `GIRTest.SymbolsDoNotDependOnTheThreadCount`).
- **Loop variables and dangling addresses (interim, manager decision M4).** A `for` loop variable has one storage for the whole loop, and so has *every* variable declared in a loop body (`x := i*10; ps[i] = &x` leaves all of `ps` pointing at one `x`: 20 20 20 where Go prints 0 10 20). Go 1.22 gives each iteration its own (spec CLO-8); the difference shows only through a closure (P04.07 builds per-iteration cells) or a pointer to such a variable kept past its iteration (P04.20 rejects that). A second hazard is not a loop one: an `&x` of a local that is stored somewhere that outlives `x` (a global, `*q = &x`, a struct a callee fills, a callee that keeps its pointer parameter) is a silently dangling stack address after the function returns; the checker refuses only the direct `return &x` (E0278), and no rule is added for a few of the ways (a partial rule is the patch-one-case pattern): P04.20 owns the whole analysis. Both Done-whens are in the TODO.
- **Not yet.** Evaluation order where Go leaves it open: an operand that is a variable is read where its expression is lowered, gc reads it after the calls of the same statement (`println(x, g())` with `g` changing `x`). The same for a failing check: when an index or division check and a call are in one statement, gc makes the call first and Go++ checks where the operand is lowered (`x = a[n(9)] + f()`, `println(a[n(9)], f())`, `x = n(1)/n(0) + f()`, `a[b[n(9)]] = f()`: Go++ panics before `f` prints). The spec leaves this order open (EXP-3), so the differential corpus keeps such statements out or tags them. (An index target on the left of an assignment is not in this list: its check is part of the store and follows the spec, see "Assignment order".) Out-of-range float to integer conversions saturate (D4.12), where gc's result depends on the target (`run/core-sat.test` has its own expected output).
- **`println` / `print`** (`Body::lowerPrintln`, D4.11 e: the bootstrap writes to standard output). Go evaluates every operand before the call, so the operands that are not constants are evaluated first, left to right, a variable into its own temporary; then the text is written. A constant operand is formatted when the program is built (an integer in decimal, a bool, a string's bytes), and the text from one value to the next, println's spaces and newline included, is one call of C `write`. Values call GIR helpers written once per module (`gopp.print_i64`, `gopp.print_u64`; a bool is a branch between two writes). Floats, complex numbers and pointers use `gopp.print_f64` and `gopp.print_hex` (Go's `+1.500000e+000` format).
- **`@Extern("C")`** (`Lowering::declareFunction`): the attribute takes the one string `"C"`, the function has no body, and its parameter and result types are C types; a Go++ string, slice, map or view, also held by value in a struct or an array, is refused first on the checker's types (P04.05 review R5: a map and a view of a struct are one pointer in GIR), in the words of `CTypeRules`, which refuses the string, slice and map types again (V067), so each problem is one E0442. The rest is decided (`gir::CTypeRules`, the same rules as V067): scalars, pointers (also `Option[*T]`), structs (nested, with arrays) or empty structs, passed as Clang's classification says (P04.11, `docs/design/c-abi.md`); an `Option[T]` by value with a non-pointer `T` and a complex number (no C type until P07 defines how Go++-only types map to C), a string, slice, tuple, several results, a top-level array, an array of zero-size elements, nesting over 64 levels, more than 4096 fields when the structs are written out or a size over 1 GiB is invalid; a func value as a parameter of an `@Extern` function is a callback (P04.18): its type is a C function pointer (`fn "C"`), C is given a C function as itself and a top-level Go++ function's C-ABI thunk (`_GPTC` + the function's symbol, linkonce_odr, made once), and a closure, a method value or a variable is E0439 naming P04.07, and a func value as a result or field, or an `@Export` function with a func parameter or result, is E0439 naming P04.07; `@Export("C")` makes a thunk with the declared C name, and a C name that starts with `_GP` is E0445 for `@Export` and E0442 for `@Extern` (SYM-4); the C name `main` is the entry point's. Anything else is `err_gir_extern_bad` (E0442) at the attribute, and calls of the function are not reported again. A program that declares `write` itself shares it with println when the type is println's (`func write(fd int32, p *byte, n uint) int`), and gets E0442 at the println otherwise.
- **The program.** `LowerOptions::Entry` (a program): package main must have `func main` (else `err_gir_no_main`, E0443, Go's wording, at the package clause), and the module gets the C entry point `main` that calls the package's init function (when it has work) and `main.main`, and returns 0. A package that is not main is lowered without an entry (an object); `gopp build` refuses to link it into an executable.
- **Stack discipline (P03.26).** The builder recurses once per level of the checked AST; the parser bounds the height of a declaration (`ParseOptions::MaxHeight`, 1024). Measured in the sanitizer build, a level costs up to 7.1 KB (a left-deep `x + x + ...` or `b && b && ...` chain at the limit needs 7.1 MB, near the 8 MB of a main thread), so `lowerPackage` runs the builder on a thread with a 32 MB stack (only the touched pages use memory; without the thread it runs on the caller). Everything after the builder (the verifier, dead-block removal, the printer, the bitstream, the LLVM lowering) is iterative. `DeepChain.*ThroughGIRAndLLVMAtTheParserLimit` (`tests/unit/GIR/DeepTest.cpp`) nests every form the subset lowers as deep as the parser allows and lowers it through GIR and LLVM IR, also under ASan.
- **Strings, slices, views and maps (P04.05).** `LowerStr.cpp` lowers them, `RuntimeStr.cpp` and `RuntimeMap.cpp` write the runtime they call, in GIR, with the small emitter of `RtEmit.h`. Each runtime function is internal to the module and made on first use (`Lowering::rt(RtFn)`); libc comes through `Lowering::libc` (`write`, `exit`, `malloc`, `calloc`, `realloc`, `free`, `memmove`, `memset`, `memcmp`). P05 replaces the bodies and keeps the calls.
  - **Values.** A string is `String(ptr, len, cap)` (24 bytes; a literal, and a part of a string made by slicing, has cap 0: it owns no buffer); `[]T` is `Slice(ptr, len, cap, alloc)` (32 bytes, ADR-0029; `alloc` is a `*u8`, the allocator object or null for the global allocator). `View[string]` and `View[[]T]` are `Tuple(ptr, len)` (also a borrowed `[]T` parameter, ADR-0029) and have no capacity (SLC-12): `cap(v)` is `len(v)`. Other views are `Ptr(T)`. Slicing a slice, an array or a pointer to an array, and `unsafe.Slice`, give a view (the checker types it a borrowed `[]T`, SLC-8: its capacity is its length), slicing a string a view of it. An explicit `View[T](x)` is the view an implicit conversion makes (`Body::makeView`). A map is `Ptr(Struct "gopp.map")`.
  - **The allocator word (P04.25, ADR-0029).** An owned `[]T` is four words, `Slice(ptr, len, cap, alloc)` (32 bytes; `Type::numFields` is 4, `fieldType(3)` is `*u8`, the checker's `unsafe.Sizeof([]int{})` is 32 and `LayoutTest` compares it with the LLVM data layout for `[]T`, a struct that holds a slice and an array of slices), and a map header (`gopp.map`) has an eighth field, its allocator. A string stays 24 bytes and always uses the global allocator. The word is chosen once, when the value is made: `make`, literals, conversions, `append` on a nil slice, a map made by `make`, a literal or the first write to a nil map get a null word (the global allocator, ADR-0027), and only the test intrinsics below (until P05.03's `mem.MakeIn`) make another one. Growth and free use the value's own word: `append` passes it to `gopp.grow_slice` and keeps it in the result, an in-place re-slice keeps it, `gopp.map_grow` allocates the new tables and frees the old ones in the header's allocator, `gopp.slice_clone` (the routine P04.09's `Clone` calls) stays in the allocator of its slice, and `gopp.slice_free(alloc, p, cap, esz)` and `gopp.map_free(info, m)` (what P04.09's drop glue calls, after the drops of the elements) return the buffer, or the entries, the index and the header, to it. `copy`, element writes, `delete`, `clear`, lookups, `range` and the copy-in and copy-out of a call's map-entry arguments allocate and free nothing (the scratch table of more than eight entry arguments is the runtime's own and global). **Borrowing drops the word:** a borrowed `[]T` parameter (no `move`; `Lowering::sliceBorrowed`, the same rule as `mapByPointer`) has the GIR type `Tuple(ptr, len)` and the caller builds the pair from fields 0 and 1 of the slice (`Body::argAs`); the callee works on a slice local of its own, `Slice{p.0, p.1, p.1, null}` (capacity = length, SLC-12), which nothing reads the word of: the checker refuses `append` and moving out of a borrowed slice (PAR-1, OWN-R3a) but accepts `xs.Clone()` on one, and that clone uses the global allocator because the word was dropped (ADR-0029 point 7; the same for a clone of a part `s[i:j]`), and a view is the pair (or the pointer) anyway. A view or a part of a slice never reads the word either (`v := s[1:]` builds its pair from fields 0 to 2); an in-place re-slice reads it where it builds the shorter slice. A `move []T` parameter and a result are the four words. `sliceBorrowed` is the one rule for the pair: P04.18's `Lowering::passOf` (the internal calling convention, D4.4) asks it for the View mode, which a borrowed string shares (`(ptr, len)`, its callee variable `String{p.0, p.1, 0}`), and P04.06/P04.07 (methods, func values and closures, whose `Func` types must give a borrowed `[]T` parameter the same pair) reuse it through `passOf`. The C ABI refuses a slice or a map in a C signature as before (V067, E0442). The deferred item: the real allocator API (`mem.Allocator`, `mem.Arena`, `mem.MakeIn`) is P05.03; the table below is the contract it fills.
  - **Allocator.** `gopp.mem_resize(ptr, size, zero)` is the one entry point of the global allocator: every byte a string owns comes from it, and so does a slice made with a null word (`make`, a literal, a conversion; size 0 is one byte, so a pointer is never null; `zero` asks for zeroed memory). Today it calls `malloc`, `calloc`, `realloc`; P05 makes it mimalloc (ADR-0027) without touching a call site. `gopp.mem_free` is its partner. Slice and map memory with an owner's word goes through `gopp.mem_resize_in(alloc, p, old, size, zero)` and `gopp.mem_free_in(alloc, p, size)`: a null `alloc` is `mem_resize` / `mem_free`; otherwise `alloc` points to an allocator object.
  - **The allocator object (P05 D5.3 has the same text).** The object starts with its function table (alloc, resize, free), inline, then the allocator's own state:
    ```text
    offset  0  alloc   func(self *u8, size u64, zero bool) *u8                  a new block of size bytes (zeroed when zero)
    offset  8  resize  func(self *u8, p *u8, old u64, size u64, zero bool) *u8  p is a block of old bytes it made; the result keeps min(old, size) bytes
    offset 16  free    func(self *u8, p *u8, size u64)                            p is a block of size bytes it made
    offset 24  the allocator's own state (an arena's chunks, a user allocator's fields)
    ```
    `self` is the object. The entries take scalars only and are called through the pointer with the C ABI of that signature (a `bool` extended as C passes it), so an allocator written in C or C++ fits: since P04.18 their types are C function pointers (`fn "C"`, the convention is part of a `Func` type) and the counting allocator's entries are C functions with GIR bodies (V075), so the call stays the C one while Go++ calls Go++ with its own convention (swiftcc, ADR-0030) (`tests/gir/allocword-view-fold`, the `LL` lines). The runtime reaches the table in one place, `gopp.mem_resize_in` and `gopp.mem_free_in` (`RuntimeStr.cpp`): it never passes a size of 0 (it passes 1), never a null `p` to `free`, calls only the table's `alloc` (a non-null `p` for `mem_resize_in` is a compiler bug and panics; resize through the word is TODO P05.05), passes to `free` the size the block was made with, and turns a null result into the `runtime: out of memory` panic. A block is aligned for every Go++ type (8 bytes). No runtime routine resizes a block yet (`append` allocates a new block and copies, as gc does, and `mem_resize_in` takes `p == null` only; P05.05 adds resize through the word); an arena's `resize` may grow a block in place or allocate and copy, and its `free` may do nothing. At `opt` 1 and above LLVM inlines the null-word path of `mem_resize_in`: where the word is a known null the call folds to the global allocator's `calloc` (`tests/gir/allocword-view-fold`, the `O2` lines).
  - **Test intrinsics (`-test-intrinsics`).** Until P05.03 has arenas, `gopp build -test-intrinsics` (hidden; `LowerOptions::TestIntrinsics`) makes an `@Extern("C")` declaration named `gopp_test_<stem>[_<suffix>]` one of the compiler's intrinsics (`LowerTest.cpp`; the declared signature gives the element type): `make_slice(which, len, cap)`, `make_map(which)`, `clone_slice(s)`, `free_slice(s)`, `free_map(m)`, `count(which, what)` (the calls so far of allocator `which`: 0 alloc, 1 resize, 2 free) and `word(s)` / `word_map(m)` (which allocator the owned slice or map has). `which` 0 is the global allocator (null word; its counters are bumped by `mem_resize` / `mem_free`), 1 and 2 are two counting objects (table, then one counter per entry, in module globals `gopp.test_alloc.N`); the `which` of `make_slice` and `make_map` may also be declared `*byte`, an allocator object of the test's own (`tests/unit/GIR/AllocatorTest.cpp` passes one written in C++). The pointer of a slice moves only when the new capacity or length is not zero.
  - **Go++ slicing rules.** `s = s[i:j]` on the same owned slice (recorded by the checker, `Info::Reslices`) shrinks it in place (SLC-6, SLC-7): the slice is read after the other right sides and the kept elements move down after the statement's stores ("Late reads" above), so `s, x = s[1:], s[0]` reads `s[0]` where it was and `s, s[0] = s[1:], 50` writes the old `s[0]`, in either order; the capacity stays. Every part over a backing store the slice does not own is borrowed, decided by the checker (SLC-8, `Checker::sliceExpr`): a part of an array, of a pointer to an array, of a defined slice type (which keeps its name), and `unsafe.Slice`; so `t = t[1:]` on one re-points it and never moves the array's elements. A borrowed `[]T` variable is re-pointed instead (PAR-2). A bound of an owned slice past its length panics, also within its capacity (SLC-13: the elements past the length are not live; `with length N`; past the capacity it is Go's `with capacity N`). The three-index form is lowered for arrays and pointers to arrays only (SLC-13); on a slice or a view it is one E0439 naming the rule (the checker accepts it: a checker gap). A borrowed `[]T` parameter (one without `move`) gets the slice's length as its capacity (SLC-12; it arrives as the pair `(ptr, len)` of D4.4, P04.25 above).
  - **Growth.** `append` grows as gc's `growslice` does (`nextslicecap`, then `round_up_size` through Go's malloc size classes and the malloc-header rule for types with pointers over 512 bytes), so `cap` after an append equals `go run`'s for every element size on both targets (`tests/run/coll-diff-append.test`: 36 element types; a Go++ string is 24 bytes where Go's is 16, so `[]string` growth is checked against Go's for a 24-byte element with a pointer). `copy` is `memmove` (overlap is safe). The `append` result is not an owned temporary.
  - **Strings.** `+` flattens a chain into one `str_concat` of the operands (iterative, a 1000-term chain does not recurse); `==`, `<` and the rest call `str_eq` and `str_cmp`; the eq/hash glue of `Glue.h` handles strings, so structs, arrays and `Option`s of strings compare and hash (map keys). Conversions between string, `[]byte`, `[]rune` and `string(rune)` decode and encode UTF-8 as `runtime/utf8` does (invalid bytes are U+FFFD of width 1; surrogates and values over U+10FFFF too). `for i, r := range s` uses the same decoder. A constant of a defined string or bool type (`Name("x")`) is a constant: the checker kept its value unknown before (`Checker::representableConst`).
  - **Maps (a temporary runtime).** `map_new`, `map_find`, `map_get`, `map_assign`, `map_delete`, `map_clear`, `map_iter_init`, `map_iter_next`, `map_iter_done`, `map_grow`, `map_entry_args` and `map_entry_back` (a call's map-entry arguments) are the interface P05.06 replaces; a use site passes `gopp.mapinfo {ksize, vsize, hash, eq}` (built per use, hash and eq are the glue of the key type). `map_get` returns the address of the value or null (the caller reads a zero value then); `map_assign` takes the address of the map variable, so the first write creates the map there (ADR-0018 amendment point 5, PAR-1: no nil-map panic); `mm[k1][k2] = v` makes `k1`'s entry, and creates its nil inner map, when it stores. A borrowed map parameter passes by a hidden pointer to the caller's header (PAR-10): its GIR type is `Ptr` to the map (`Lowering::mapByPointer`, the map case of P04.18's `passOf`, decides it, for declarations and calls; methods, P04.06, and func values, P04.07, must call through the same rule; so does a borrowed struct, array or Option that holds an owning part, passed as a pointer to the caller's place, P04.18), its uses go through `Body::Aliases`, and a write creates a nil map in the caller's variable, also through several calls. A map entry passed on is a place (OWN-P9), but no pointer into a map's entries is held across a call (the callee may grow the map, and `map_grow` frees the entries; review R11): the entry is copied in and out. Each map-entry argument of a call gets one record in an array of the caller's frame (`gopp.mapentryarg`: the map info, the map object, the key evaluated once, its kind, the copied-in map, the slot the callee gets; `Body::mapEntryArg`), filled after the other arguments; one call of `gopp.map_entry_args` copies every entry in (nil for an absent key) and resolves the aliasing at run time: an entry equal to an earlier one of the call (the same map object, not nil, the same key kind and an equal key) gets that one's slot, so `two(mm[i], mm[j])` with `i == j` aliases as `two(x, x)` does, and so do three or more equal ones (reviews R12, R14). Up to 8 entry arguments are compared pairwise; above that a hash table of the distinct entries makes it O(n) expected (R15: the GIR of a call is linear in its entry arguments, `GIRStress.TheLoweringOfEntryArgumentsIsLinear`). After the call one call of `gopp.map_entry_back` copies out, once per distinct entry: a map the callee created for an entry that was there and nil is stored into it, looked up again (`map_get`) in the map object saved at copy-in (`map_grow` keeps the object, so a callee that grows the map is fine, and one that re-points the path to it, `p = &other`, does not send the map to another owner; R13), only if the key is still there and its map still nil: the creation is "in place" (OWN-P9), so when the callee deleted the key the place is gone and the key is not made again, and when it set the entry to another map that store stands (the created map is dropped). A map the callee writes that already existed is that same map, so its writes are the owner's. P04.09 must keep the saved map object alive across the call, or skip the copy-out when it was freed (TODO P04.09 item 5). **Writes that are still lost, each with its task:** an absent key or a nil outer map, decision M9 (the callee's map is its own; P04.09 item 3, an owner decision); a borrowed range variable of an owning element, which is a copy of the element's header until P04.09 makes it the element in place (P04.09 item 2); a borrowed struct, array or Option that holds a map, passed from a map entry (`put(docs["k"])`), which is a copy of the entry (P04.18 passes the caller's place, but holds no pointer into map storage across a call; P04.09 item 6 copies it back); aliasing that OWN-B4 and CON-18 forbid and the borrow checker must reject, since each copy-in is a map of its own for the call: a map and an entry of it passed together, `both2(mm, mm[5])` writing `outer[5] = other` and then its entry parameter, or `both(mm, mm[5])` reading `outer[5]` while it holds the copy, and an entry passed again under a call, `g(mm[5], mm)` calling `twof(x, mm[5])`, plus the slice twin `put(xs[0], ...)` with a callee that moves `xs` (P04.20 items 6 and 7); and a deferred or `go` call with a map-entry argument, E0439 today (P04.07). A map that is no place (a temporary) gets the write and drops it. **Open (owner, P04.09 TODO):** an entry whose key is absent inserts nothing (decision M9: an argument expression never inserts), so the callee gets a nil map of its own and its writes are dropped with it; the other option is to insert the key at the callee's first write. A slice element or a field passed as a borrowed map is still passed by its address: a callee that moves that slice's buffer (an `append` to a global slice) invalidates it, which the borrow checker must reject (P04.20, TODO item 6). Layout: dense entries `[hash | key | value]` in insertion order (hash 0 is a dead entry) plus an open-addressing index.
  - **Iteration (RNG-4, spec chapter 16).** A range visits the entries that were there when it began, from a pseudo-random one around to the one before it (`gopp.map_rand`: splitmix64 over a module state seeded once per run from a stack address), so the order differs from range to range, as in Go; an entry deleted before the range reaches it is not seen, and a map cleared during the range ends it. The map counts its running ranges: `map_iter_init` adds one, and the range ends once, when `map_iter_next` runs out or `map_iter_done` runs, which `Body::exitScopes` emits for the iterator's scope on every way out of the loop (`break`, `continue` or `break` of an outer loop, `return`) and the `goto` lowering for every range whose statement does not hold the label (`Body::labelPos`). `map_assign` of a new key while the count is not zero panics with "map insert during iteration", whatever the size of the table; writing a key that is there is no insert. A panic does not unwind yet, so the count on the unwind path is P04.07's (TODO).
  - **`range`.** Integers (every width), arrays, pointers to arrays, slices (the length is read once), strings, maps; the define and the assign forms (`for a[i] = range n`, `for k, v = range m`, each iteration one assignment with Go's two phases); the range expression is evaluated once. An array is copied first when the loop copies its elements (trivial elements, as in Go, RNG-6); when the value variable borrows the element (owning elements, `Var::Borrowed`) and in the `&` form the live array is walked. `for _, &d := range xs` (RNG-1a) makes `d` the element itself: a pointer local in `Body::Aliases` whose uses are a `Deref`, for slices, arrays, pointers to arrays and map values. A borrowed range variable of an owning element is still a copy of the element's header (the element in place is P04.09's).
  - **`unsafe`.** `unsafe.Slice`, `unsafe.String`, `unsafe.SliceData` and `unsafe.StringData` with Go's checks; the slice or string owns nothing it shows (a string's capacity is 0; an `unsafe.Slice` result has its length as capacity, and P04.09 must not free it).
  - **Not here.** Closures, `defer` and range over a function (P04.07), generics (P04.08), drops (P04.09), channels (P12). Each is one E0439 naming the task.
- **Interfaces and methods (P04.06; `LowerIface.cpp` the data and the body code, `RuntimeIface.cpp` the runtime).** The design is one set of shapes that later tasks fill in without changing: P04.07 method values (an itab slot is already a plain function pointer), P04.08 generic itabs (the symbols are `LinkOnceODR` and named by type, so an instance folds), P04.22 `extends` (field 12 of the descriptor is its type table and `Promoted` thunks are `IfaceThunk`s of another receiver), P04.23 operator methods (a method set is a list of `S::Func`, the key is where an operator name goes) and P05 reflection and `fmt` (the descriptor has the size, name, kind, flags, method table, and reserved fields for the element and the field table).
  - **Methods.** A method is a function whose parameter 0 is the receiver. A pointer receiver is the pointer: `x.M()` passes the address of an addressable value. A borrowed value receiver passes as a borrowed parameter of its type does (P04.18, review R9; `Lowering::passOfRecv`, the same rule as `passOf`, and the parameters of a method and of an itab slot's function type go through `Lowering::paramType`): a trivial value is copied before the arguments are evaluated; a string or slice is `(ptr, len)`; a value that holds a map, string or slice is a pointer to the caller's place, taken after the arguments as a Place argument's is (`callWith`'s late addresses), so `d.Put()` with a nil map in `d` creates it in `d` (PAR-1). Which place, for receivers and arguments alike, is one decision (`Body::placePath` / `placeHow`, reviews R10, R11; the table of `docs/design/calling-convention.md`): a variable, a pointer's target and a slice's element are passed by address; a value in an interface's box or a view is a copy (TYP-5, TYP-9); a map entry of a map type is copied in and out; one that holds a map otherwise is one E0439 naming P04.09 (item 6); anything else is a temporary. Through an interface the thunk passes a held pointer or its own copy of a held value (below). A method promoted from a parent type is P04.22, an operator method P04.23, a method of a generic type P04.08, `@Virtual`/`@Abstract`/`@Override` P04.22, a method value or expression P04.07: each is one E0439 (`Lowering::methodSupported`). A method marked `@Extern("C")` is E0442 (a C function is no method).
  - **Method sets come from the checker.** Which methods a dynamic type has (a value the value-receiver ones, a pointer all of them; a `move` receiver, an operator method and a generic method in none) and which methods an interface has (its type set: embedded interfaces flattened, a method that two of them name once) are the checker's decisions, asked through `sema::MethodSets` (`MethodSets.cpp`: the checker's own `lookupFieldOrMethod`, `typeSet` and `comparableType` on the checked package), never worked out again here. Once the types are final, the checker finds a method of a type with more than 8 by a name index (`NamedType::MethodIndex`, `Checker::lookupMethod`), so the method set of a type of m methods costs m log m; the lowering's step count includes these lookups (`MethodSets::steps`). A method a type has only through `extends` (a `ParentSteps` hit) is refused naming P04.22. The lowering caches each answer per type (`Lowering::methodSet`, `ifaceMethods`), sorted by key; a call finds its itab slot in one lookup (`IfaceMethods::Slot`), and two interfaces with the same keys share their itabs without a conversion (`sameItabs`, cached per pair).
  - **The interface value.** `gopp.iface` is `{ itab *u8, data *u8 }`, one GIR type for every interface type (a named struct, `Type::isIface`); `Option[I]` is the same type (D4.5: `unsafe.Sizeof(Option[I]) == Sizeof(I)`), its nil a null itab. `error` and `any` keep Go's nil (a zero value); an interface with methods is never nil (OWN-P9). A value whose layout is at most 8 bytes (including a pointer, and size 0 with data 0) lives in the data word itself (`Lowering::isInline`, the one decision point: its low bytes on both little-endian targets); any other value is copied into a new box (`gopp.mem_resize`). The box is shared and immutable (TYP-5); a copy is shallow until the clone glue of P04.09. A view and its target are different dynamic types (`View[string]` is not `string`), so a binding of an owning type in a type switch or assertion is a `View[T]` of the box (TYP-9) and only the value of a comma-ok assertion in a `View` position is lowered that way.
  - **Static data (`Global::Parts`, V072).** Descriptors, method tables and itabs hold pointers to globals and functions, which the scalar initializer of a global cannot. A global with `Parts` has a list of constant leaves (section 5 of the printer: `constdata @g: T = { const ..., ... }`; serialized as the `GlobalData` record). `PtrToPtr` also casts between a pointer and a function (V053), so an itab slot is a plain `*u8` and a call casts it back.
  - **Type descriptor (`gopp.typeinfo`, `TI::` in `LowerImpl.h`).** One `LinkOnceODR` global per dynamic type, named `Syms.glue(TypeInfo, T)` (`_GPTi<type>`), so its address is the identity of the type across modules: field 0 is its own address (so it is also the itab of `(T, any)` and converting to `any` loads `itab[0]`), then size, Go's reflect spelling of the name (`main.T`, `*main.T`, `[]int`, `map[string]int`, `interface {}`, `struct { A int "json:\"a\"" }` with a tag quoted as `strconv.Quote` does: `unicode::quote` in `Basic/Unicode.cpp`, whose `unicode::isPrint` is `strconv.IsPrint` from a table that `tools/gen-unicode` writes from Go, checked on every code point against Go's own output, `tests/unit/Basic/GoQuote.inc`), the eq and hash glue (null when the type is not comparable), the `reflect.Kind` (Option 27, View 28), the flags (bit 0: the value is in the data word), the method count and table, and the reserved element, field table and `extends` type table. The method table (`_GPTm<type>`, the MethodTable kind of appendix A) is `{ key string, fn *u8 }` sorted by key; the key is `Name \x01 [package path if unexported] \x01 mangled signature`, so two methods are the same exactly when Go says (name, and for an unexported name the package, and an identical signature).
  - **Itab.** One `LinkOnceODR` global per (dynamic type, interface) pair with methods, `_GPTa<type><interface>`: `[descriptor, thunk_1 ... thunk_n]` in the interface's sorted key order (embedded interfaces flattened; `Lowering::ifaceMethods`). A thunk (`_GPTI...`, `LinkOnceODR`) takes the data word and the arguments and calls the method, passing the receiver as `passOfRecv` says: the pointer for a pointer receiver, and for a value receiver a copy (a trivial one), the pair (a string or slice) or, for a Place receiver, an address. Through a pointer the interface holds (`&e`) that address is the pointer, so PAR-1 reaches the pointed-to value. A value the interface holds, in its box or rebuilt from the word, is immutable all the way down (TYP-5): a Place receiver gets the address of the thunk's own copy, so a map the method makes in a nil map is dropped with the copy and the box stays as it was, as with Go's value receiver (`tests/gir/recv-thunk.test`). It is named by the method as the method's own symbol is (`_GPTIM4BumpN4mainE3Box` for `(*Box).Bump`); a value method in the table of the pointer type reads through the pointer, a different thunk, `_GPTpM3SumN4mainE5Adder` (appendix A.5, P04.12 review R7). It is at the method's declaration, on the function and on each statement, so a debugger shows that line for its frame (P04.12 review R8). A conversion to `any` needs no itab (the descriptor is it). A conversion between interface types, and an assertion to an interface type, builds the itab at run time (`gopp.get_itab(desc, ti)`: a walk over the two sorted key lists) from the interface descriptor `{ name, n, keys }` (`_GPTn<interface>`, the IfaceDesc kind of appendix A). Its cache is a map of the map runtime from the pair to the itab, or to null when the type lacks a method (as Go's `itabTable`), so each pair is built once and the memory is bounded by the pairs a program meets, not by its conversions (`run/iface-itab-memory.test`); the itabs are never freed, and the cache is not synchronised (TODO P12.06).
  - **Calls.** A call through an interface checks the itab is not null (a nil `error`: Go's nil dereference), loads slot `k+1` (the interface's sorted position of the method), casts it to the thunk's function type and calls it with the data word first. The call site of a pointer is not tagged `sext`/`zext` by the callee, so narrow integers cross it through the thunk's own signature.
  - **Conversions and tests.** `valueFor` converts to an interface type (`toIface`): a concrete value is boxed with the itab of its static type; an interface to another is `ifaceConvert` (nil stays nil); an `Option[T]` becomes a nil interface when unset and the boxed payload when set; an `Option[I]` is already the words. `x.(T)` and `case T` compare the descriptor loaded from the itab with the descriptor of `T` (identity), or call `get_itab` for an interface `T`; a type switch tests its cases in source order (`nil` is a null itab) and binds the value (a single-type clause) or the interface (several types, `nil`, `default`). A failing `x.(T)` calls `gopp.panic_assert` with Go's text: `interface conversion: interface {} is string, not int`, `... is nil, not int`, `interface is nil, not main.Shape`, `main.Sq is not main.Namer: missing method Name`. `==` on interfaces is `gopp.iface_eq` (nil-aware; same descriptor; the descriptor's eq function on the two values, or `runtime error: comparing uncomparable type []int`); the hash of a map key is `gopp.iface_hash` (`hash of unhashable type`); `println` of an interface prints `(itab,data)`. A comparison of an interface with a concrete value or another interface type converts the other side to the interface with fewer methods. An `Option[T]` or `Option[J]` where an `Option[I]` is wanted goes through the same conversion (`Option[I]` is the interface: nil stays nil, a set one is boxed or gets its itab for `I`). The results of a call with several results convert to the types they go to (`Body::convertResult`): `return f()`, `a, b = f()`, `var p, q any = f()`, a package variable, and `g(f())`; so does a comma-ok form's value (`a, ok = m[k]`, `a, ok = x.(T)` with an interface `a`). The eq glue takes the addresses of its operands, so a call's result (`f() == err`) is copied first (V066). A lookup or a delete of a key that holds an interface calls `gopp.map_key_check` first, which hashes the key in a nil or empty map too, as Go's `mapKeyError` does; an unhashable dynamic type then panics with that path's words, `hash of unhashable type: []int` (any other hash says `runtime error: hash of unhashable type []int`). The words come from a module flag (`gopp.plain_hash`) that `map_key_check` sets around the hash: the unwind path must clear it once a panic can be recovered (TODO P04.07), and goroutines race on it (TODO P12.06).
  - **Borrowed interface parameters (D1.12, D4.4, TYP-8): not done; a deviation from D4.4.** D4.4 passes an interface parameter as `(itab, data)` with a borrowed tag, so a call that only borrows its interface argument allocates nothing. Here every conversion of a value larger than a word boxes it into an owned box (`gopp.mem_resize`), argument or not (and so does each `...any` element), and the box leaks until P04.09's drops. The itab word's low bit is reserved as the borrow tag and every reader masks it (`itab & ~1`), so the caller's tagged `(itab | 1, &value)` and the callee-side "keeps it" analysis can be added without changing a reader (TODO P04.09, "Borrowed interface parameters", with its both-sided Done-when).
  - **Views in interfaces (TYP-9, OWN-V).** A boxed view keeps the dynamic type `View[T]` (`case T` does not match it; its descriptor is its own, named `View[T]`), and compares and hashes as the value it shows: the descriptor of a `View[string]` holds `str_eq` and the string hash through its `{ptr, len}`, that of a view of another comparable type the glue of that type through the pointer (`Lowering::viewGlue`); a view of a slice or a map is not comparable (`run/iface-views.test`, `panics-gopp/eq-view-slice`).
  - **Known gaps.** A struct or an array that holds a view (an `@View` struct) is not comparable in an interface: its eq glue is made from the GIR type, where a view is its words, so it would compare the words where OWN-V compares the values (the same glue makes a direct `h1 == h2` of such structs shallow today; reported to the manager in the P04.06 ledger). The Go text `(types from different packages)` of a failed assertion is not produced; an interface type with a type set (a constraint) used as a type is one E0439.
