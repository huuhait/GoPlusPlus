- **P04.22 `extends` lowering (ADR-0023)** (owner decision 2026-10-28; spec TYP-20 to TYP-24, EXP-13 to EXP-15, OWN-R2; depends on P03.22 and P04.06; docs already written). Lowers the checked hierarchy:
  - *Layout.* The type-table pointer (one word, first) exists only for a type that has, or inherits, a `@Virtual` or `@Abstract` method; then the parent part, then the child's fields. If a child adds the first virtual method to a parent without a table, the child has the word and the parent part follows it; the borrowed upcast adds a fixed offset, and the owning upcasts to that parent are errors. The upcast is free, at most a fixed address adjustment: the same address when the parent has a table or neither has one, a fixed offset when the child adds the first virtual method. Final-only hierarchies have no table and no overhead.
  - *Type tables.* One table per type with a table (`linkonce_odr`): the entries of the virtual methods (the nearest override), the drop function, the size, and the parent's table for downcasts. Tables are emitted once and deduped across packages.
  - *Calls.* A call through a parent pointer to a `@Virtual` or `@Abstract` method is indirect through the table; every other call (final methods, `base.M()`, calls on a known concrete type) is direct and can inline. The call from a final parent method to a virtual method (`Total` calls `Fee`) is indirect.
  - *Upcast and downcast.* An upcast is free, at most a fixed address offset (`View` and a borrowed `*Child` when the child adds the first virtual method; the owning kinds `Unique`, `Shared` and `Weak` exist only when the parent has a table, so they keep the same address). A downcast `p.(*Card)` checks the table chain and panics, and `x, ok := p.(*Card)` gives `ok = false`. There is no table in a final-only hierarchy: the checker (P03.22) already rejects the owning-pointer upcasts and the downcasts there, so the lowering needs no dynamic type for them.
  - *Drop order.* The child's `drop`, the child's fields in reverse order, then the parent part; destroying a `Unique[*Parent]` that holds a `Child` runs the child's drop through the table. Moves and `Clone` use the whole value.
  - *Interfaces.* Itabs of a child contain the overrides; inherited methods are reached through the parent part.
  - *Debug info and tools.* DWARF has the base class link for debuggers (P04.12); the field table includes the parent chain (TYP-10).

Rejected at the GIR verifier: a direct call to an `@Abstract` method; an upcast between unrelated types.
- **P04.23 Operator lowering (ADR-0024)** (owner decision 2026-10-28; spec EXP-16 to EXP-30, RNG-6b, CON-22; depends on P03.24 and P04.06; docs already written). Lowers the checked operator expressions:
  - *Calls.* Every operator expression on a user type becomes a direct call of the resolved method: `a + b` is `Vec2.+(a, b)`, `a != b` is `!(a == b)`, `a < b` is `(a <=> b) < 0`, `x op= y` is a call of the in-place method when the type has one (no allocation), else `x = x op y`, with `x` evaluated once in both; `x++` is the `++` call. The built-in `<=>` on numbers and strings lowers to the `cmp.Compare` sequence (two compares, no call; floats handle NaN). Operands are passed as borrows, the result is an owned temporary dropped by the usual rules. Operand order follows the source, also for `@Right` (the swap changes only the argument positions).
  - *Symbol names.* Operator method names are mangled by a fixed table (`+` as `op_add`, `[]` as `op_index`, `[]=` as `op_setindex`, `<=>` as `op_cmp`, `@Convert` by target type), including the overload's parameter types; P04.17 lists the table.
  - *Inlining.* Operator calls are ordinary calls and inline like any small method (the `@Inline` rules of P04.13). A `Vec2` loop of `a + b` compiles to the same IR as hand-written field math (FileCheck).
  - *`&&` and `||`.* The eager form is a call after both operands. The lazy form builds a non-escaping closure for the right operand and passes it; if the method does not keep it, it is inlined with the method (the right side runs only on the path that calls it). Built-in `&&`/`||` on `bool` are unchanged.
  - *Index, call, deref, conversion.* `a[i, j]` read is a `[]` call, a write is a `[]=` call with `v` moved in, `a[i, j] += v` is one `[]` and one `[]=` call with `a` and the indexes evaluated once. `a(x)` is a call, also under `defer`/`go`. `*a` is the `*` call. `R(a)` is a call of the `@Convert` method.
  - *`range` and channels.* `for v := range t` calls the `range` method once, then lowers as range-over-func (P04.07). `q <- v` and `<-q` are calls of the `<-` methods; no scheduler support is needed, the methods are ordinary code.
  - *Generics.* Monomorphization (P04.08) resolves the operator elements of a constraint to the instance type's real method, or to the built-in operation for built-in types (`Sum[int]` emits an `add`).
  - *Debug info and tools.* DWARF names the operator functions with the source spelling (`operator+`), so debuggers show `Vec2::operator+`.
  - *Done when:* GIR dump and run tests pass. Accepted: the ADR-0024 examples print the expected values (`Vec2` sums and `@Right`, `Matrix` index and compound forms, a `Queue` with `<-`, `10*units.Km + 500*units.M` with constants from a second package, `Sum` over `int`, `Vec2`, `BigInt`); FileCheck on the GIR and LLVM IR shows a `Vec2` `a + b` inlined to two `fadd` instructions with no call and no allocation, and `Sum[int]` has no call to a method; a lazy `&&` runs its right side zero times when the method does not call the closure, and an eager `&&` runs it every time; `c += b` evaluates a side-effecting `c` expression once; for a `Matrix` with an in-place `+=`, `m += n` makes no allocation (leak counter), and for a `Matrix` without it `m += n` allocates one temporary and drops the old value; `1.0 / v` through a `@Right` `/` method gives the swapped-order result, and a `@Right` on a commutative `*` gives `2.0 * v == v * 2.0`; unary `-v`, `+v`, `^x`, `!f` through their methods; `==` and `!=` (`!=` is the negation of the same call); `x++` and `x--` on a user type; `*a` returning a `View[Vec2]`; `float64(b)` through `@Convert`; `a(x)` and `defer a(x)` and `go a(x)`; `[]=` on a non-Matrix type (a ring buffer); `v, ok := <-q` through a `(R, bool)` receive method; `extends`: an inherited `+` called through a child value and a pointer-receiver `()` operator replaced with `@Override` and called through a `*Parent` (dynamic dispatch); `m += m` is a checker error (P03.24), so lowering sees only `m += n`; `<=>` on `int`, `string` and `float64` with NaN gives -1/0/1 as `cmp.Compare`; `a[f()] += v` calls `f` once; a `BigInt` `+` allocates exactly one result and the temporary is dropped at the end of the statement (leak check); an operator panic unwinds with destructors run; a `range` method over an `iter.Seq` loops and `break` works; the differential tests (P04.14) run a `.go` counterpart written with methods (`Add`, `Mul`) and match the output.
- **P04.24 Units lowering (ADR-0025)** (owner decision 2026-10-28; spec UNI-9, UNI-12, EXP-32 to EXP-37; depends on P03.25, P04.04 and P05.08; docs already written). Lowers the checked unit code:
  - *Erasure.* A unit type has the type, layout, alignment and calling convention of its base kind; GIR types carry no unit. A unit literal is the number. Arrays, slices, maps, channels and structs of unit types are lowered like those of the base kind (the mangled symbol names include the unit type so that generic instances and overloads do not clash; P04.17 lists the rule).
  - *Scale conversions.* A conversion between units of one dimension is one multiplication by the exact factor rounded once to the base type (an integer kind: a checked integer factor, wrapping `*`). Constants are folded exactly before rounding. A product or quotient with an empty dimension and a factor is a multiplication by the factor. Conversions that do not change the scale emit nothing. `+`, `-`, `%`, `min`, `max` and comparisons with a scale difference convert the coarser operand to the finer unit with one multiplication by the ratio (a constant); constant operands are folded exactly. Compound assignment converts the right operand to the unit of the target (a multiplication by the ratio, or for floats a constant factor). An explicit integer conversion to a coarser unit is a signed division by the integer ratio (truncating, `sdiv`/`udiv`; a power of ten is a multiply-high sequence after LLVM), and for a non-integer ratio a widened multiply and divide.
  - *Generics.* Monomorphization (P04.08) treats a unit parameter as a compile-time value: `Avg[KM]` and `Avg[M]` are two instances with the same code, deduplicated by the base kind when the code is identical (the mangled names differ, the bodies are merged by P06 dedupe).
  - *`fmt` metadata.* A unit type that is boxed in an interface gets a type descriptor (P05.08) with its base kind, the canonical form (base-unit exponents and the factor) and the display form with the `@Symbol` texts; descriptors are interned so one descriptor exists per canonical form, and the printed display form is the one chosen by the fixed order of UNI-5. `fmt` (`%v`, `Print`, `Println`) prints the number as the base kind and then the unit (UNI-12); the numeric verbs print the number only; `%T` prints `float64[KM]`. A type switch compares descriptors; a named unit type has its own. Types that are never boxed have no descriptor and no cost.
  - *Debug info.* DWARF describes a unit type as its base type with the name `float64[KM]`.
  - *Done when:* GIR dump, LLVM IR and run tests pass. Accepted: the ADR-0025 examples print the expected values (`50 KM/H`, `100500 M`, `float64[KM/H]` through `%T`); FileCheck on the LLVM IR shows `d + 500.0[M]` (with `d` in `KM`) as one `fmul` by `1000.0` and one `fadd` with no call, the same for `500.0[M] + d`, `d += 500.0[M]` as one `fadd` of `0.5`, `int[M] += int[KM]` as one `mul` by 1000 and an add, `int[KM](m)` as a truncating `sdiv` (`int[KM](int[M](1999))` gives 1 and the negative case gives -1 in a run test), `speed.In[M/S]()` as one `fmul` by a constant, and `Travel(speed, t)` as one `fmul` with no call and no extra instruction compared with the same code on plain `float64`; a loop over `[]float64[M]` vectorizes like the same loop over `[]float64` (FileCheck on the vector IR); the struct `Vec2[KM]` has the size and layout of `struct{ X, Y float64 }` (`unsafe.Sizeof` / `Offsetof`); integer scale conversion `int[M]` to `int[MM]` is one `mul` with an integer constant; `d / 500.0[M]` for `d` in `KM` is `fmul` by 1000 and `fdiv`, and gives `200`; the same unit written as `KM/H`, `KM*H^-1` and a unit declared as `1000 M / 3600 S` produces identical IR; `fmt.Println` of a `float64[KM]`, `float64[KM/H]`, `float64[KG*M/S^2]` (`KG*M/S^2`), `float64[1/S]` (`1/S`), `float64[KG/(M*S)]`, `complex128[A]` (`(1+2i) A`) and an `int[M]`; the numeric verbs `%f`, `%.2f` and `%d` print no unit; a `@Symbol("km")` unit prints `km`; two spellings of one type print the same text in every build order (a test builds the packages in two orders and in parallel); `%+v`, `%#v` and `Sprint`/`Sprintf("%v")`/`Sprintln` print the same number and unit as `Println` (`%#v` prints the type and the unit, e.g. `float64[KM](100) KM` fixed by the golden test), also for a struct field and a slice element of a unit type (`{X:1 KM Y:2 KM}`, `[1 KM 2 KM]`); a named type with `String()` prints through the method; `any(d)` matches `case float64[KM]` and not `case float64`; boxing a `float64[KM]` and a `float64[M]` makes two descriptors, and boxing the same canonical form from two packages makes one; a program with no boxed unit type has no unit descriptor in the binary; a cross-package program using `units.KM` and `units.M` from a second package gives the same output as the one-package version; the generated stress program (10 000 unit conversions) compiles in near-linear time.
