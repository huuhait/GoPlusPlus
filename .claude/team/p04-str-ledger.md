Manager decisions (PM merge):
- M1 base c3: the `Rec` nominal GIR type (self-naming bodies; serialized; V002/V003), the single allocator entry `gopp.mem_resize` + `gopp.mem_free` for P04.09, the stable map runtime interface (`map_new/find/get/assign/delete/clear/iter_init/iter_next/grow` with `gopp.mapinfo`), `Local::Owned` marks (V014) for P04.09's drops, strings/slices/views as places. Reject c1's wrapper-struct recursion (c3's `Rec` is the reusable design).
- M2 nil maps follow the Go++ spec, not Go: a write to a nil map creates it in place (ADR-0018 point 5, EXP-7, PAR-1) — c3 is right, c1/c2's "nil map write panics" programs become positive tests (the write works) and their Go goldens are not used for those cases (hand goldens, marked). Writes into a temporary map or a map inside an interface are checker errors already (check).
- M3 map iteration order is random per `range`, as in Go (spec chapter 16: "Map iteration order (random, as in Go)") — c3's insertion order must change (e.g. a random start bucket/offset and wrap, per `iter_init`). Tests stay order-independent; add a test that every entry is visited exactly once from any start, and one that two ranges over a map of many keys do not always agree (bounded, deterministic seed hook for tests if needed).
- M4 RNG-4 exactly as specified: maps count their active iterators; inserting a NEW key while any range over that map is running always panics with "map insert during iteration", independent of table size; writing an existing key is allowed; `mm[k1][k2] = v` with an absent `k1` panics. Both sides tested (c3's best-effort version counter is not enough).
- M5 port from c2: its edge tables (every invalid UTF-8 form, append growth for every element family incl. the 24-byte-string stand-in, map tombstones/growth/NaN keys/±0 keys, delete during range, shared-prefix compares, copy overlaps), the V003 guard for a type holding itself by value (`type A [2]A` — c2 found a possible infinite loop in `structsIn`), the Option-of-pointer-to-own-type fix (`payloadAs`, run/recursive-option), `&` range aliases (RNG-1a) if the checker accepts them, its panic programs (minus the nil-map-write ones per M2). From c1: its distinct panic programs (makeslice, convert, range index), `for a[i] = range` targets, `data-optkeys`. One set of verifier rule numbers; one runtime DSL (pick the cleanest of the three `RtDsl/RtEmit`).
- M6 slice layout stays 3 words `{ptr, len, cap}` as P04 D4.5 says. Spec SLC-1 says an owned `[]T` is 4 words (with an allocator word) — a conflict between D4.5 and SLC-1 that the owner must decide (manager will ask); do not implement the 4th word here; record the open question in gir.md section 15.
- M7 SLC-12/SLC-13 and three-index slicing on arrays only follow the Go++ spec (borrowed `cap == len`, re-slicing past len panics). Go goldens are used only where Go and Go++ agree; Go++-only cases have hand goldens marked `// GOLDEN: by-hand`.
- M8 gates: counted work in the normal suite, timing only in `.long`; normal tests < 2 s; arm64 subset normal, full matrix long; report times with `uptime`; the manager measures the 60 s ASan limit and suite time at merge. The runner (P04.19), C ABI (P04.11) and opt (P04.13) merges run in parallel; whichever merges later rebases.
